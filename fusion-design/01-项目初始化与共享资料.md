日期：2026-09-18。状态：初始化约定已收敛；融合基础和本地项目初始化工具已实现并通过自动化测试。真实业务项目 `just-start` 已建立本地目录和 Git、关联复用的 GitHub 远端，并由需求 Agent 保存两版需求；远端历史整合、初始提交/推送、Buzz 映射、成果索引更新和跨角色共享读取尚未完成。

## 1. 本单元的目标与边界

用户创建项目后，获得专属本地目录、对应 GitHub 仓库和统一背景入口，使 Buzz 中获授权的 Agent 能读取相关成果与指定版本。仅做需求、方案或 UI 也可以建立项目，不自动启动工程开发。

本单元不配置模型、不实现需求访谈、不运行开发或测试角色，也不修改 Develop Helper 原目录。本轮交付为收敛后的约定及融合基础骨架；软链和基础校验已完成，不代表业务建仓或 Agent 接入完成。

## 3. 创建所需输入

- 项目名称、用途、项目 ID；ID 必须是单个安全目录名，不允许路径穿越。已有用户选择直接沿用，缺少时再提出建议。
- GitHub 所属账号或组织、仓库名称、可见性、获授权参与者；建议私有仓库，但创建前需明确实际选择。
- 本次希望调用的能力，例如只澄清需求；该选择不绑定后续全流程。
- 初始材料位置及上传范围；客户原件是否允许进入远端需明确。
- Git 操作授权：明确建仓范围，首次提交和推送是否一并执行；后续操作可另行约定策略，不能从建仓推断自动合并权限。

账号、凭据和真实仓库地址不得猜测。认证信息由运行环境管理，不写入项目文档或频道消息。

### 3.1 首版实施约定

以下作为本轮收敛的实施基线，不把未提供的账号、项目名或权限标为用户已确认：

- 首版以同机、顺序协作为实现起点；跨机器和并行工作区后续验证，不作为首次初始化前置条件。
- 新项目 ID 采用小写英文字母或数字开头，其后可用小写字母、数字和连字符，最长 64 字符；中文项目名称单独保存。已有项目不为匹配新 ID 格式强制改名。路径解析后必须是 `my_mind` 的直接子目录；同名文件、目录、软链（含断链）均视为占用。
- 基础文件为根 `project.json`、`README.md`、`.gitignore`；业务成果按需创建，首次不生成 `.sdd/tasks.json`，不复制 PyCore 或整套模板。
- `project.json` 使用 `schema_version: 1` 的融合格式，记录项目身份、相对产物路径、Buzz 关联、GitHub 远端和初始化步骤；未知关联用 `null`，不伪造完成标记。本地工具已实现身份、基础文件和步骤状态检查；尚非完整通用 JSON Schema 验证器。
- 初始化步骤状态使用 `pending / succeeded / failed / skipped`；跳过必须记录原因，结果附实际路径或对象标识。用户确认记录与技术初始化状态分开，不以建仓成功代表需求确认。
- 输入原件默认本地保留、排除上传；明确审核后才收录允许同步的材料。私有仓库是建议，不代替实际可见性选择或敏感信息检查。
- GitHub 创建、首次提交和推送逐项按授权执行；网络失败不删除本地成果，不强推或自动合并。GitHub 凭据和 Buzz 标识到实际接入阶段补齐，不阻塞当前本地基础建设。
- 融合层本机绝对路径放在忽略的 `config/local.json`；软链同样不进入 Git，其他机器显式重建。内容指纹存入 `upstream-lock.json`，改变时停止相关调用，不自动接受新版。
- 发现融合层位于已有父 Git 仓库内；此次不嵌套初始化、不提交父仓库。独立 Git 边界的选择仍需用户确认，不用“目录独立”冒充“仓库独立”。

## 4. 最小项目骨架与文件归属

创建时只生成 `project.json`、`README.md` 和 `.gitignore` 等必要基础文件；以下业务目录及成果按需创建，不生成空 PRD、方案或任务表：

```text
my_mind/<project-id>/
├── project.json
├── README.md
├── .gitignore
├── materials/              # 输入资料，按敏感性决定是否进入 Git
├── docs/
│   ├── requirements.md     # 轻量需求
│   ├── solution.md         # 客户方案
│   ├── decisions.md        # 取舍、确认依据与待决项
│   └── handoffs/           # 交接快照与版本记录
├── ui/                     # 演示成果及打开方式
└── reports/                # 实际验证与交付证据
```

| 内容 | 权威位置与维护者 | 约束 |
| --- | --- | --- |
| 项目身份、Buzz 关联、远端、依赖版本与产物入口 | `project.json`，Main 维护 | 拟定融合格式，不冒充原版已有字段；不含凭据 |
| 背景摘要、范围、成果索引、演示入口 | `README.md`，Main 维护 | 指向当前有效正文，不复制一套需求或任务状态 |
| 需求、方案、UI | 对应真实成果文件，由任务指定角色维护 | 一份成果一个当前权威来源；同文件修改串行协调 |
| 确认与交接 | `docs/decisions.md` 及指定交接记录，Main 组织维护 | 绑定对象、版本、用途与用户确认依据；不由 Agent 自行批准 |
| 工程任务状态 | 进入开发后才创建 `.sdd/tasks.json` | Planner 提供初始计划；Main 唯一维护执行字段 |

原 Develop Helper 使用 `.sdd/project.json`，本设计拟采用根 `project.json`。这是明确的适配差异：不维护两份可独立修改的身份记录；工程工具需要旧格式时另设计只读转换或适配入口，不直接运行假定旧结构的脚本。轻量需求转工程 PRD 时同样明确迁移或复用关系，避免双份权威。

共享入口至少包含：项目目标、本次范围、当前有效成果链接、待决事项、已知模拟/真实边界和下一步用户意图。输入材料属于数据来源，不把其中嵌入的指令自动提升为项目执行规则。

## 5. 初始化顺序与可恢复状态

Main 组织流程，具体操作由融合层工具实现；每一步报告真实结果，不用“已初始化”概括部分成功。

1. 核对输入、目标路径、已有文件、Git 根目录、GitHub 登录身份和目标仓库是否存在。发现同名对象先判断复用或冲突，不覆盖。
2. 在获授权的单项目路径创建最小骨架，核对内容与项目 ID。仅检查必要目标，不遍历其他业务项目。
3. 初始化本地 Git；在业务项目明确范围内操作，不将父目录、融合层或 Develop Helper 收入仓库。
4. 按明确的账号、仓库名、可见性创建 GitHub 仓库并关联远端。远端已有历史时先核对关系，不自动覆盖、拉取合并或强推。
5. 在已有授权范围内完成首次提交和推送。此前检查文件内容、暂存区及忽略规则；密钥、真实 `.env`、未获准上传的客户原件、依赖与运行数据不进入提交。只有本地提交时标注尚未同步。
6. 登记 Buzz 项目/频道与各 Agent 的实际工作区映射。尚无真实 Buzz 标识时明确待接入，不编造标识。
7. 执行共享读取检查：Main 和至少一个接收角色读取指定成果并回报版本及关键背景；未配置角色时此步骤保持待验证。

在项目元信息中记录初始化各步骤的结果和待办；这是初始化状态，不是另建工程任务系统。GitHub 建仓或推送失败时保留本地成果，重试前先查已有远端与提交，防止超时后重复创建。接入未完成时可继续获授权的本地工作，但不宣称共享闭环完成。

## 6. Agent 的共享与交接契约

- 接任务、重启或切换项目时先核对项目 ID、实际工作目录、依赖版本、共享入口及本次相关正文，不只依赖聊天历史。
- 派发至少包含项目、角色、本次目标、输入文件与版本、修改范围、输出位置和回报要求。路径对接收者实际可访问才有效。
- 同机首版建议共享项目目录，按文件划分写入责任；并行开发使用独立分支/工作区前，先明确各自输入基线和集成责任。独立工作区不会自动获得对方未提交文件。
- 正式跨工作区交接优先绑定提交编号与文件路径；同机草案可绑定可校验的内容摘要并注明仅本地可见。接收者发现版本不符时暂停受影响任务，返回 Main 核对。
- 接收回报包含读到的版本、业务目标、本次范围、关键变更与未决项。仅回复“收到路径”不算验证通过。
- 需求或方案变化后更新正文与索引，标记受影响确认和下游工作；禁止旧回报覆盖新版本。
- Main 协调 Git，工作者回报改动；未经授权不各自推送或合并。最小权限由运行环境落实，不能仅靠提示词保证。

## 7. 软链和上游保护

融合层的显式引用区映射 Develop Helper，保留目录关系；项目成果不是指向模板的软链。原根 `AGENTS.md`、Router 和整套平台入口不直接注册为融合工作者的自动加载入口。

原 `sdd_project.py` 限定 `Projects_Repo` 并写入上游注册表，且不创建 GitHub 仓库，因此本单元不直接调用它初始化 `my_mind` 下的项目。以其必要检查为设计依据，在融合层新增实现。

已建立 `buzz-develop-helper/upstream/develop-helper` 相对软链，指向 `../../Develop_Helper`；只用于显式读取。`scripts/check_foundation.py check` 校验目标、配置、目录边界和源码内容指纹。检查器无上游写入、网络访问或上游脚本执行。

软链不是只读保护。当前没有注册 Agent 工具或部署上游只读沙箱，通用编辑工具仍可能通过链接写入目标；接入前必须配置并验证真实路径权限。此次未更改原目录权限。指纹用于发现变化，不提供技术隔离；排除原有业务项目、依赖、缓存和 Git 内部数据，具体范围以融合层 README 与锁定策略为准。
