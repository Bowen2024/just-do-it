### Buzz 运行态验收协作约定

Buzz 中的发消息、创建或切换线程及其他界面操作，默认由用户执行。负责融合建设的主会话应输出可直接复制的消息正文、发送位置、是否使用顶层消息或回复，以及预期结果；用户回传界面结果后，主会话再核对日志、文件或源码证据。除非用户明确要求主会话直接操作 Buzz，否则不使用计算机控制执行这些操作，以避免不必要的上下文和 token 消耗。

## 4. 固定恢复顺序

每次继续融合建设时按以下顺序恢复，不从聊天摘要直接推断状态：

1. 读取本文件。
2. 读取 `00-拆解与融合框架.md`。
3. 读取“当前状态”指定的编号文档；当前先读 `02-需求能力.md` 和 `05-项目成果索引与确认交接.md` 恢复既有边界，再读 `03-方案能力.md` 继续当前单元。
4. 读取 `../buzz-develop-helper/AGENTS.md`。
5. 读取当前能力对应的 `capabilities/`、`adapters/`、脚本和测试。
6. 需要核实原框架时，先检查上游指纹，再读取 Develop Helper 相关原文。
7. 需要核实 Buzz 能力时，读取相关源码并区分“源码支持”与“实例已启用”。
8. 只有执行具体业务任务时才读取相应业务项目；业务项目不保存融合系统测试方案。

发生冲突时不使用一个笼统的优先级：设计意图看融合设计文档，已实现行为看代码和测试，运行状态看实测证据，业务事实看业务项目文件。用户的新决定若尚未落盘，只能视为待固化，不能长期依赖会话记忆。

## 5. 新单元设计门禁

本门禁适用于新建融合单元，或对既有单元进行会改变阶段、权威产物、角色责任、自动衔接或完成标准的实质重构。只修改错字、链接或不改变语义的状态说明时不要求重写整份设计。

### 5.1 固定顺序

1. 按第 4 节恢复总索引、总框架、当前单元及相关已实现边界，先确定本次目标、非目标和验收范围。
2. 运行 `../buzz-develop-helper/scripts/check_foundation.py check`；上游软链、路径或指纹不一致时停止引用，不自动刷新基线。
3. 使用 `../Develop_Helper_reading-guide/` 定位当前模块涉及的 Skill、Agent、Protocol、Template 或脚本；阅读指南只作导航和解释。
4. 回到 `../Develop_Helper/harness-core/` 相关原文核实权威方法。不得用阅读指南、聊天摘要或已有融合草案代替上游原文。
5. 在当前编号设计文档中完成“上游来源、原样继承、Buzz 必要适配、新增建议、暂不建设、验收范围、来源追踪表”。使用 [单元设计门禁模板](module-design-template.md)，并运行设计契约检查。
6. 没有上游依据的阶段、等级、权威文件、角色责任、自动调度或完成标准必须标为“新增建议”，记录 `待确认 / 已确认 / 已否决 / 不采纳`。待确认内容不得实现为默认行为。
7. 用户确认新增设计后，才在 `../buzz-develop-helper/` 建设 capability、adapter、确定性工具和测试；软链只用于只读引用，不自动加载或执行上游入口。
8. 需要 Buzz 承载时，再核对并修改 Buzz 源码，区分源码支持、release 构建、实例启用和运行态验收；四者不能互相替代。

### 5.2 设计契约检查

新建或实质重构的单元文档在进入实现前运行：

```sh
python3 -B ../buzz-develop-helper/scripts/check_design_contract.py check <单元设计文档>
```

检查器只验证必要章节、上游原文引用、来源追踪表和新增建议的确认状态是否存在；不能判断业务语义正确，也不能代替用户确认。既有单元在未实质修改前不要求追溯重排；一旦实质重构，应先补齐本门禁。本轮单元 03 是首个采用该门禁的实例。

### 5.3 四类事实仍须分开

- `fusion-design/` 说明决定建设什么；
- `buzz-develop-helper/` 的文件和测试说明融合层实际实现什么；
- Buzz 源码和构建说明宿主具备什么；
- 当前实例实测说明现在真正启用了什么。

设计文档通过门禁不等于实现完成；本地测试通过不等于生产实例已启用。

## 6. 收尾触发协议

触发语（标点差异不影响）：

> 兄弟，今天就到这里吧。

当用户在融合建设会话中说出该触发语，当前主建设 Agent 应在本轮结束前执行以下动作：

1. 检查本轮实际修改、测试结果、用户确认、被否决方案和新增风险。
2. 更新本文件的“当前状态、下一步和更新时间”。
3. 更新本轮涉及的编号设计文档；只修改真实受影响的章节。
4. 若实现状态变化，更新 `../buzz-develop-helper/README.md` 及相关 capability/adapter；没有变化则不改。
5. 若源码变化，运行与变更相称的检查并记录真实结果；失败不得写成通过。
6. 业务项目只记录真实业务事实和成果，不写入融合能力测试计划或聊天总结。
7. 检查不同文档中的状态表述是否冲突，明确保留尚未验证和已知限制。
8. 向用户报告更新了哪些文件、当前停点、下次从哪里继续。

收尾触发语不授权 Git 提交、推送、建仓、合并、删除文件、修改 Develop Helper 上游或执行其他破坏性操作。这些动作仍需用户单独明确授权。该协议由收到触发语的主建设 Agent 执行，不由需求、方案、UI、Developer 或 Tester 等业务角色自动执行。
