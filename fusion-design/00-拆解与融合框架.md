### 3.1 四个独立板块的调用边界

| 板块 | 可接受的起点 | 本次可独立交付 | 后续按需衔接 |
| --- | --- | --- | --- |
| 需求 | 客户材料、访谈纪要、已有需求或一个业务问题 | 场景、现状痛点、目标流程、范围、成功标准、待澄清事项；进入工程时再补齐所需 PRD 结构与编号 | 方案、UI，或结束本次工作 |
| 方案 | 需求成果，或用户直接提供且足以支撑方案的业务材料 | 面向客户的业务/能力方案、架构说明、关键流程、实施路径、假设与待决取舍；工程级接口和数据契约按需深化 | UI、工程设计/规划，或结束本次工作 |
| UI | 已有需求、方案、页面说明、参考界面或明确的演示场景 | 可展示页面/原型、打开方式、演示步骤、模拟数据说明和实际验证范围 | 展示、修改、需求反推、工程开发，或结束本次工作 |
| 确认与交接 | 任意已有产物及本次希望确认或交接的用途 | 对象与版本、确认者及依据、未决项、模拟/真实边界、下游必需补齐项 | 记录后结束，或在用户要求下交给指定能力 |

独立调用仍要求本次目标所必需的信息；缺少会改变结果的事实时定向澄清，草案中的假设明确标注，不伪造已确认需求。已有材料可直接使用，不强制重新执行其产生阶段。

“确认与交接”是统一处理产物版本及用途的能力，不额外设置每次都要执行的审批阶段。确认用于客户展示，不等于批准真实接口实现、外部调用或发布。

### 3.2 轻量化与按需深化

- 只澄清需求：交付需求成果即可，不自动生成完整技术方案或开发任务。
- 只输出方案：先满足客户交流用途；七层工程方案作为需要实施时的深化方法，不要求每次全部填满。
- 只做 UI：根据足够的页面与演示信息制作；可以使用明确标注的模拟数据，不以真实后端完成作为展示前提。
- 只确认/交接：核对指定产物与用途即可，不自动启动后续智能体。
- 开始工程开发：检查已有成果，只补相关 PRD/AC、工程契约、设计确认和环境缺口，再接入任务规划、开发与独立测试。

轻量需求说明、客户方案与 UI 演示均不自动等同于原 Develop Helper 中 Confirmed PRD、Confirmed tech-spec 或前端 Mock 门禁通过。转入工程时按实际产物覆盖范围核对。

上述解耦是本次融合的目标变化：原框架的 A → 七层方案 → 必要 B → Planner 顺序作为工程路线保留参考，独立交付路线需要新增入口和适用规则；原源码尚未实现这些入口。

### 3.3 项目初始化与共享资料

**创建项目即建立资料归属和版本管理，不必等到开始开发。** 一个项目对应一个专属本地根目录和一个 GitHub 仓库；仅澄清需求或制作演示也使用该项目目录，但不因此生成完整工程模板、开发任务或启动后续角色。继续已有项目时复用已确认目录与仓库，不重复创建或覆盖原有内容。

建议的最小目录约定如下；除项目元信息、共享入口和忽略规则外，其他目录与文件随实际成果按需创建，不要求填空模板：

```text
<项目目录>/
├── project.json             # 项目身份、Buzz 关联、仓库地址与产物入口（拟扩展字段）
├── README.md                # 所有 Agent 的项目背景入口及成果索引
├── .gitignore               # 不进入 Git 的资料、密钥、运行产物等
├── materials/               # 输入资料；区分本地保留和允许同步的内容
├── docs/
│   ├── requirements.md      # 轻量需求；工程化时沿用或迁移，避免双份权威
│   ├── solution.md          # 客户方案；工程级 tech-spec 按需另建并说明关系
│   ├── decisions.md         # 已确认取舍、确认对象与版本、待决问题
│   └── handoffs/            # 指定成果的版本与交接记录
├── ui/                     # 可展示 UI、素材及运行/演示说明
└── reports/                # 实际产生的验证证据、测试与交付报告
```

工程代码位置沿用项目实际技术结构；进入工程后才按需建立 `.sdd/tasks.json`。现有项目不为符合示例而重排目录，在索引中登记实际路径即可。大型素材或不宜进入 Git 的资料可保存在受控本地目录或批准的存储位置，由索引记录安全引用与访问条件；“统一管理所有项目信息”不等于“所有文件全部上传 GitHub”。

初始化与协作规则：

1. **建立项目映射。** Main 组织初始化，先核对项目名称、本地位置、GitHub 所属账号/组织、仓库名、可见性和访问范围；建议私有仓库，具体选择在实际创建时确认。检查现有 Git 根目录与远端，避免误用父仓库、嵌套建仓或覆盖已有历史。项目级身份与映射以 `project.json` 为准，各运行环境的绝对路径另行映射，不假定跨机器相同。
2. **提供统一上下文入口。** `README.md` 简述业务目标、本次范围、当前工作概况，并链接有效的需求、方案、UI、确认记录和演示方式。它是导航与摘要，不复制所有正文，也不另建工程任务状态。Main 维护索引与映射；各角色维护职责范围内的成果。
3. **接任务先读背景。** 每个参与 Agent 启动、恢复或接新任务时，读取项目入口和本任务相关文档。Main 派发时附项目标识、实际工作区、输入路径与版本、修改范围和回报要求；接收者先验证能读取这些文件。仅加入同一个 Buzz 频道或配置同一个仓库地址，不代表已经加载项目背景。
4. **明确本地共享与远端同步。** 同机首版可共享项目根目录，按文件分配写入责任，同一文件修改串行处理。需要并行编码时再采用独立分支与 worktree；它们不会自动共享其他工作区的未提交内容。跨机器或隔离环境通过已批准推送的提交同步，各自映射本地路径；开始任务前核对基线，不自动覆盖脏工作区或解决冲突。
5. **绑定可验证版本。** 正式跨角色交接优先使用提交编号和文件路径；同机尚未提交的草案可用文件内容摘要等快照标识交接，并注明仅本地可见。接收者读到相同输入版本才算交接成功。需求变更后由 Main 标出受影响的确认与下游任务，不能让旧分支成果悄悄覆盖新需求。
6. **集中协调 Git。** Main 组织 Git 操作并核对范围，工作者默认回报修改与证据，不各自无约束地提交、推送或合并。实际创建项目时执行获授权的建目录、初始化 Git 和创建仓库；后续 commit、push、PR、merge 按明确授权或用户另行约定的策略执行，建仓不自动批准所有后续动作。
7. **资料分级与最小权限。** 密钥、真实 `.env`、访问令牌和未获准上传的客户原件不进入远端；提交前核对内容与忽略规则，私有仓库也不是免检理由。各 Agent 只获得本项目所需的文件、工具和仓库权限；GitHub 仓库权限与本地文件权限分别验证，提示词中的限制不能替代权限控制。
8. **如实记录初始化状态。** 本地目录、Git 初始化、GitHub 建仓、远端关联、授权的首次提交/推送、Agent 读取检查分别记录结果。远端失败时可保留本地成果并继续获授权的本地工作，但不得标记为“远端已同步”或“全体 Agent 已共享”；重试先检查已有结果，避免重复建仓。

共享背景依赖“资料落盘 + 入口索引 + 版本约定 + 读取与同步机制”，GitHub 提供版本保存和分发，不自动同步聊天记忆，也不保证所有 Agent 实时看到同一份未提交文件。

### 4.1 从单平台主会话编排，调整为 Buzz 跨工具编排

原 Develop Helper 并非要求一个智能体亲自完成全部工作：平台主会话进入 Router 后组织全流程，再按协议派发 Designer、Planner、Developer、Tester。现有 .codex/agents/developer.toml 已是引用核心 Developer 规则的薄适配器，.claude 和 .cursor 也有相应角色入口。

融合目标将流程组织权放到 Buzz Main Agent，需求澄清优先在 Buzz 内直接进行；外部 ChatGPT 可提供补充需求成果，方案讨论仍保留原有外部入口。执行环境可以不同，能力也可单独调用：

| 接入对象 | 接收的内容 | 职责与完成后的去向 |
| --- | --- | --- |
| Buzz 需求澄清 Agent | 客户材料、提取后的需求方法、角色提示词、历史需求摘要和必要文档工具 | 使用 GPT 与用户直接澄清、保存草案和定稿；按需向 Main 交接，不自动启动方案或开发 |
| ChatGPT 外部讨论（需求可选入口、方案当前候选入口） | 当前客户材料、需求/方案方法、选定的交付格式 | 和用户形成成果；将版本及确认依据随文件交接，不承担后台调度 |
| Buzz Main Agent | 用户本次意图、已交接成果、入口路由、产物状态及适用的调度规则 | 路由到需求澄清或其他能力，核对成果与使用范围；维护交接及工程执行状态，不逐句转述需求对话 |
| Codex UI 执行会话 | UI 方法、演示目标、页面说明、素材、修改范围与展示检查项 | 交付演示页面和验证范围，回报 Main；不自动开始后端开发 |
| Codex Planner 会话 | 已确认的相关设计、工程约束、任务模板与规划角色规则 | 返回任务计划，不自行接管后续调度 |
| Codex Developer 会话 | 当前任务、相关需求与技术章节、Developer 规则、适用工程规范和修改范围 | 实现与自验后回报 Main，由 Main 决定是否派 Tester |
| Cursor Tester 会话 | 当前任务、AC、代码基线、测试环境与 Tester 规则 | 独立验证并回报 Main，不重新执行项目初始化或需求访谈 |

工具配置目录只负责使运行环境发现和读取适用指令，不能用目录存在来证明角色已被启动。融合版需明确区分“用户新请求”和“编排器已分配的角色任务”，防止角色任务再次进入完整 Router。

实现时要核对实际会自动加载的根 AGENTS、平台规则与角色提示词：通过独立融合入口的加载范围解决冲突，不修改 Develop Helper 原入口，不依赖工作者忽略已加载的上层指令。项目通用工程约束继续适用。

“避免多套角色规则”指融合版角色职责保留一个权威入口，Buzz 提示词和工具薄适配器引用它；能兼容的内容引用上游，必要差异仅在融合层维护。不复制全套原规则到每个角色，也不同时加载相互冲突的执行指令。融合差异需明确记录，不能把新行为描述成原框架已经支持。

### 4.2 软链复用与独立融合适配层

采用“上游原件不动 + 软链引用 + 独立融合适配 + 项目成果独立保存”的结构。融合层位于 `/Users/bowen/Desktop/博文的career/vibe- coding/buzz-develop-helper`，不放进 Develop Helper 原目录。下列基础目录和指纹锁已建立；角色入口、能力实现及项目初始化脚本仍待建设：

```text
Develop_Helper/                  # 上游来源，融合流程不写入
buzz-develop-helper/
├── upstream/develop-helper -> <已核对的 Develop Helper 路径>
├── adapters/                    # Buzz 与各运行环境的薄入口
├── capabilities/                # 独立需求、方案、UI 等能力的适配规则
├── scripts/                     # 新项目初始化、链接校验等新增实现
└── upstream-lock.json           # 拟定：上游版本、依赖文件摘要与兼容记录
<业务项目目录>/                  # 需求、方案、UI、代码等真实成果及独立 Git
```

1. **软链只解决定位，不改变规则。** 上游资料放在显式引用区，不注册为整套自动加载的 Skill/根入口。可直接兼容的文件才作为执行规则引用；存在耦合的文件作为方法依据，由融合层写出明确、完整的适配指令，记录来源、采用范围与差异。不能“先加载全流程，再要求忽略其中步骤”。
2. **不修改上游包含间接写入。** 软链不是只读保护，经链接编辑仍会修改目标。融合执行应通过工具权限、沙箱等限制上游写入，并检查调用脚本是否会写注册表、活动项目、日志或经验目录；无法保证不写入的脚本不直接执行。不能为接入而擅自更改原目录权限或文件内容。
3. **保留引用关系并验证实际解析。** 优先保留上游目录结构的映射，避免零散链接破坏相对引用；逐个验证 Markdown 相对链接、脚本定位及运行环境的真实路径解析。需要真实路径的调用显式解析上游位置，输出路径始终指向业务项目或融合层，不从脚本所在目录推定输出位置。
4. **版本记录不等于版本锁定。** 首版记录实际使用的上游版本及文件摘要；上游未提交的改动也需识别。运行前发现漂移时暂停受影响能力并评估，不能继续声称使用旧版本。需要可复现环境时，将软链指向单独准备的固定版本只读副本，不切换或重置用户的原工作区；上游升级后验证适配差异再更新记录。
5. **跨机器需要重建依赖映射。** Git 通常保存软链的目标路径而非目标内容，克隆融合仓库不会自动获得 Develop Helper。记录依赖来源与版本，本机路径通过环境配置管理；各运行环境安装匹配依赖并重建、验证链接。断链、权限不足、系统或工具不支持软链时明确报错，不静默使用其他版本。
6. **项目成果不采用上游软链。** 需求、方案、UI、确认与测试记录均保存为业务项目真实文件；模板只作读取来源。业务仓库记录所用融合版本与上游版本，其他 Agent 仍按第 3.3 节读取同一份项目背景，不能用规则共享替代成果共享。

示例：需求能力复用阶段 A 的澄清方法和按需 R 调研，但在融合层定义轻量交付、保存目录及结束条件；原 A 中的全量 PRD 要求与自动派发 Solution Designer 不因此生效。新项目初始化也由融合层实现，不能靠软链让原脚本自动具备任意项目目录或 GitHub 建仓能力。

## 5. 角色方案与用户工具偏好

| 职责 | 首选方式 | 参与时机与边界 |
| --- | --- | --- |
| Main Agent | Buzz 中独立编排会话，运行环境待定 | 判断本次交付目标，只调用必要能力；维护确认与交接，进入开发后维护执行状态 |
| 需求澄清 | Buzz 内独立需求 Agent，优先采用 buzz-agent + 可用 GPT 模型；外部 ChatGPT 可选 | 与用户直接多轮澄清、记录变更并保存需求成果；可单独交付，不与方案角色强制合并 |
| Solution Designer | 优先用户与 ChatGPT 讨论 | 输出适合当前用途的方案与取舍；工程深化时核对仓库事实及接口契约 |
| UI 制作 | 优先评估 Codex 使用提取后的 UI 方法 | 生成可展示页面并验证实际交互；不默认承担真实后端实现；工具选择是候选建议 |
| Planner | 按阶段启动独立规划会话，优先评估 Codex | 设计确认后形成完整计划；执行后只提出计划调整 |
| Developer | Codex | 开发并自验；需要并行时拆前端/后端实例；不改验收口径或执行状态 |
| Tester | Cursor | 独立形成用例、执行验证、返回证据；不修改业务实现和需求以取得 PASS |
| 用户 | Buzz 中的项目参与者；方案讨论可暂留 ChatGPT | 确认需求、重要取舍、必要界面与规定的成果门禁 |

角色、运行环境、模型分别配置：角色定义工作职责，运行环境提供会话与工具执行，模型负责推理和生成。角色不等于软件，也不等于永久在线进程。同一种工具可以承载多个隔离的角色会话。

首版路线：创建项目时先建立专属本地目录与对应 GitHub 仓库，或核对并复用已有项目；登记共享入口及各 Agent 的工作区。用户在 Buzz 中与需求 Agent 直接讨论，草案与定稿保存到项目目录并更新成果索引；确认后按用户意图交接给方案或 UI 能力，也可就此结束。方案讨论暂保留外部 ChatGPT 候选入口；Buzz Main Agent 按需调用 UI 制作，进入开发后调度 Codex 与 Cursor。确认与交接主要由 Main Agent 组织，无需为其单设常驻智能体。外部 ChatGPT 成果可通过文件进入同一交接机制，不以对话自动同步为前提。

### 5.2 需求对话、定稿与交接

1. 接收本次材料与目标，复用已有内容，确定本轮只澄清需求或还需后续交付。
2. 围绕使用者、现状问题、目标流程、范围和成功标准追问，每轮集中处理少量关键缺口；不预设客户没有提供的事实。
3. 持续区分已确认事实、待确认假设和未解决问题。用户修改要求时更新相应内容，保留必要变更说明，受影响的旧确认不继续作为当前依据。
4. 根据用户要求或已约定的交付目标整理轻量需求文档。草案可以保存并结束，不强制填满工程级 PRD 或生成任务清单。
5. 需要定稿时展示具体版本与未决项，记录用户确认的对象、用途及消息依据。文档由需求 Agent 维护；Main 核对并记录交接范围，不重复索取已有有效确认。
6. 回报 Main 的内容包含产物位置、版本、确认依据、变更摘要、未决项及用户要求的下一步。交接时核对路径对接收者实际可访问；没有继续请求则结束本次工作。

Main Agent 不逐句中转用户和需求 Agent 的讨论；它负责路由和成果交接。需求 Agent 不管理工程任务状态，也不替代用户批准方案、开发或发布。

## 6. 状态与交接的设计原则

1. 所有已创建项目均有专属本地目录及对应 GitHub 仓库。单独需求、方案、UI 工作只维护所需产物、索引、版本和必要记录，不要求创建完整工程目录或 .sdd/tasks.json；本地保存、Git 提交与远端同步状态分别说明。进入工程开发后，建议保留 .sdd/tasks.json 为任务执行状态权威，Main Agent 唯一维护执行字段；Planner 提供初始计划。Buzz Issue/频道可展示或提交变更请求，不成为另一套独立状态来源。
2. 工程路线保留 REQ → AC → Feature → Task → 验收证据的关联；项目身份和所选规范以 project.json 为准。轻量成果进入该路线时补齐必要映射，不虚构其此前已通过工程验收。
3. 派发信息需关联项目、任务、角色、执行轮次、目标身份、工作区、代码基线、输入章节、修改范围和验收要求。
4. 结果需关联原派发、实际运行记录、修改产物、验证证据与未完成事项。去重键、租约或运行标识的具体存储位置在单元 08 设计，不提前新建平行业务状态库。
5. 相同任务重复送达不得导致重复实施；旧轮次结果不得覆盖新轮次；未知运行状态先核对，不直接重派。
6. 角色提示词中的修改范围属于工作约定，是否通过工具或文件权限强制限制要单独设计，不能把提示词当作已实现的隔离。
7. 用户确认需要绑定确认者、对象、版本和确认事件。普通回复、其他智能体认可或模糊表情不自动放行。
8. 原框架的前端门禁、逐步模式和有限返工用于相应工程路线；独立 UI 演示交付不自动触发全项目后端配置门禁。独立路线的适用范围是本次明确的解耦目标，具体实现后再验证。

- Buzz 需求角色已完成多轮触发、自主按需调研、三版文档落盘、历史保留、来源摘要校验和只读恢复；A/R 自动切换与用户最小输入已固化为角色契约，并通过自动化测试及 Buzz 运行回归。需求单元已范围内关闭；项目索引、确认、固定快照和交接/回执已有本地内核，融合层可信上下文接收与工具隔离已有临时夹具验证，Buzz 生产挂载和 first-mate Main 绑定已进入运行实例。保留字段和角色工具面拒绝已实测；错误项目/多个项目/线程换项目因混合批次隔离缺口未通过，业务写入和跨角色读取仍待完成。
- 用户已确认线程隔离开关启用，恢复回复准确读取落盘最新版本；同项目不同线程的运行实例边界仍缺少独立日志，不能只靠回复内容证明完全隔离。

- 已查看的 Buzz Workflow 代码会将审批步骤标为 approval_not_supported。首版不依赖其完整审批恢复能力，可由 Main Agent 与 SDD 门禁记录承接，后续验证实现方案。
- 项目初始化需验证本地目录、GitHub 建仓与远端关联、资料忽略规则和失败重试；本框架中的初始化字段与机制尚未实现。
- 同频道不代表共享文件系统。验证各 Agent 能读取项目索引与指定版本；同机按文件分配写入责任，跨工作区/跨机器核对提交同步和路径映射，覆盖冲突、旧版本与未提交文件不可见的情况。
- Main Agent 停止时，工作者可能仍运行；恢复必须先核对在途任务和产物。

## 8. 拆解推进顺序与统一记录格式

先补齐 01 的项目初始化与共享资料入口，随后围绕用户工作重心细化 02 需求、03 方案、04 UI、05 确认与交接。再处理 06/07 的角色与事实归属；08/09/10 按试点所需补齐运行闭环；11 先验证独立交付，再验证工程衔接。这是设计工作顺序，不是用户调用顺序。

每个单元只形成一份短设计，统一记录：用户调用意图、最小必要输入、可复用材料、具体操作、独立交付物、完成条件、按需衔接方式，以及原机制与文件依据、Buzz 能力、适配缺口、验收方式和待决问题。同时标明“直接软链引用”“仅作方法依据”“融合层新增/改写”的分类、上游版本和差异，不修改上游文件。区分“原有事实”“融合建议”“已确认决定”“已运行验证”。

## 9. 最小试点与通过条件

首个试点聚焦“项目初始化 + Buzz 内 GPT 需求 Agent + 共享成果读取”，不等待开发调度全部完成。先创建试点项目的本地目录和 GitHub 仓库，核对权限、共享索引与授权的首次同步。提供一份文字或 Markdown 客户材料，进行连续多轮澄清，在途中修改一项已讨论的要求，保存并确认定稿，重启需求 Agent 后恢复，再按用户明确请求把同一版本交给 Main/下游角色。接收角色需实际读取并正确复述关键范围、最新变更和未决项，而不只是收到文件路径。需验证：关键事实未丢失、旧要求已被正确替换、确认对象明确、文档实际可读取、没有自动启动方案或开发。模型调用成功或仓库创建成功都只是接入检查，不等于共享需求工作流通过。

第一层优先验证解决方案工程师的日常工作，使用同一业务场景分别验证独立调用与成果复用：

试点前先验证融合层依赖：链接可读取且引用解析正确，上游版本匹配，自动加载入口不触发原全流程；比较运行前后的上游文件状态，确认没有由融合操作产生的写入。模拟断链和版本漂移时，应明确停止受影响调用，不自动换源或修写原目录。

| 场景 | 通过条件 |
| --- | --- |
| 项目初始化 | 专属本地目录、Git 仓库、GitHub 远端与 Buzz 项目映射正确；敏感资料不被收录；已有项目不重复建仓，失败时状态如实保留 |
| 共享项目背景 | 需求 Agent 与接收角色实际读取同一版本的项目入口及成果；跨工作区时核对已同步提交，未提交文件不冒充已共享 |
| 只澄清需求 | 在 Buzz 中由 GPT 需求 Agent 连续澄清并保存可读取的需求成果；无需外部 ChatGPT 中转，不自动启动技术方案、UI 或开发 |
| 需求变更与恢复 | 修改要求后，文档与确认状态同步反映变更；重启后能从已保存成果恢复，不混用其他话题 |
| 只输出方案 | 使用已有业务材料形成可对客讨论的方案，列出假设与取舍，不强制完整工程规格 |
| 只构建 UI | 使用现成页面说明生成可展示页面，实测展示和关键交互，明确模拟范围，不要求先重做需求与方案 |
| 只确认与交接 | 记录指定产物的版本、用途和未决事项，不重复询问已有有效确认，不自动推进下游 |
| 组合执行 | 需求成果可继续用于方案、方案可用于 UI；只补下一步需要的缺口，不重新跑上游全量流程 |

第二层再选择一个小型 Web 业务项目，复用上述成果，补齐必要工程契约后验证前端 Mock、一个真实后端能力与联调。所需角色按阶段参与，先顺序执行，再在模式允许时验证前后端并行。

工程试点必须覆盖以下场景：

| 场景 | 通过条件 |
| --- | --- |
| 正常交付 | 确认方案 → 规划 → 开发自验 → 独立测试 → 联调 → 交付，产物可追溯 |
| 缺陷返工 | Tester 给出可复现证据，Developer 定点修复，Tester 复验，保留重试次数 |
| 前端门禁 | 必须等用户确认当前 Mock 与必要配置；暂停期间不新增未经允许的派发 |
| 中断恢复 | Main Agent 重启后识别已有执行与成果，不重复开发 |
| 重复与迟到消息 | 同一派发只实施一次；过期回报不覆盖新结果 |
| 验证条件缺失 | 标明具体未验 AC 与恢复条件，不用 Mock 冒充真实通过 |

独立交付优先比较从材料输入到可用成果的耗时、不必要的确认/文档数量、跨板块复用情况和用户介入次数；工程试点再比较交付耗时、有效缺陷数及模型/工具消耗。相似任务的对比用于判断是否继续扩展，不把一次试点当作普遍效率结论。

## 10. 第一轮需要收敛的设计选择

这些问题在相应拆解单元中处理，不阻塞当前框架整理：

- 融合适配层位置已确定为 `buzz-develop-helper`；如何单独版本管理？哪些文件能直接引用，哪些需要只保留方法并编写适配规则？
- 上游版本如何记录、固定和升级？各运行环境如何重建软链及限制上游写入？
- 需求成果中哪些信息是客户交流必需的，哪些只在进入开发时补齐？
- 方案侧重业务讲述、总体架构还是工程落地，如何按本次任务选择深度？
- UI 以页面展示还是可点击的完整演示为目标，如何明确模拟范围？
- GPT 需求 Agent 首版采用哪个具体模型，凭据和文档工具如何配置？
- 需求对话怎样触发、按线程隔离和恢复，如何更新项目内的成果索引？
- Buzz 内定稿与可选外部 ChatGPT 成果怎样走同一版本/确认交接机制？
- Main Agent 使用哪个运行环境，如何在 Buzz 中接收工作者结果？
- 业务项目父目录已确定为 `/Users/bowen/Desktop/博文的career/my_mind`；GitHub 使用哪个账号/组织、仓库命名和可见性策略？
- 首版是否同机执行？不同 Agent 的目录访问、写入范围和跨工作区版本同步如何验证？
- 项目资料如何分级，哪些允许上传？后续提交、推送和合并采用怎样的明确授权策略？
- Tester 可使用哪些浏览器、命令和隔离测试数据？
- 首个独立交付试点使用哪个客户场景？后续转入工程时需要补齐哪些条件？
