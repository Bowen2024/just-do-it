## 4. 测试环境和夹具

### 4.1 三种源码／配置环境

1. **S0 未改动来源**：原 `fusion-runtime/`、原上游和原配置只读。使用基线 JSON 核对，不在此处注入故障。
2. **S1 未配置的开发测试源码**：`_work/project-path-explicit-20261103/` 为唯一开发副本。排除真实 `local.json`、迁移备份和缓存，保留方法相对软链。现有发布完整性测试在此运行。
3. **S2 已配置的临时安装**：复制已审查代码、方法与来源记录到临时安装；业务目录为安装树外的另一临时位置。所有配置变更、权限故障、候选与事务都在这里进行。

S1、S2 的开发实现必须相同。为 S2 生成配置不会成为“源码出现真实配置”的测试失败原因。上游故障只注入临时伪上游；完整原上游若使用只读软链，运行前后核对摘要。

### 4.2 目录布局

```text
<TEMP_ROOT>/case-<id>/
├── install/SA-mate/
│   ├── Develop_Helper/
│   └── fusion-runtime/workflows/{requirements,Solution Designer,UI}/
├── legacy-root/                 # R，旧模式父目录
├── external-a/项目A/            # X/A，E模式目标
├── external-b/项目B/            # Y/B，E模式目标
├── external-a/同名项目/
├── external-b/同名项目/
├── imports/                    # IMP，独立授权外部源
├── denied-source/              # 未授权源
├── other-workdir/              # 进程从安装树外启动
└── evidence/                   # 本用例原始协议、摘要、结果
```

所有临时根先 resolve，避免 macOS `/var` 与 `/private/var` 的正常别名造成假失败。业务父目录默认不处于已有 Git 仓库；Git 解耦专用用例才创建临时 Git 父仓。

### 4.3 模式和项目状态矩阵

| 模式 | 配置 | 合法目标 |
| --- | --- | --- |
| E | `project_path_mode: explicit`；保留、缺失或失效旧根／映射 | X/A、Y/B 等明确完整位置 |
| L0 | 完全缺少模式字段 | R 的合法直接子目录及既有映射 |
| L1 | `project_path_mode: legacy_rooted` | 同 L0 |
| CONFIG | 空值、非法类型或未知模式 | 应在配置阶段拒绝 |

项目状态至少覆盖 missing、empty、initialized、nonempty_uninitialized、corrupt；目录名称覆盖 ASCII、中文、空格和不同父目录同名。初始化成功的合法项目优先使用实际初始化能力构造，不手写不完整元数据冒充合法夹具。

L0/L1 不照抄“R外成功”预期；以 R 内对应合法布局验证兼容，并单独断言 R外／孙目录拒绝。文档读写与 Git 分离是本次明确调整：旧测试若把“父仓存在即读写失败”视为预期，应替换为“合法文档操作成功＋非法建仓仍拒绝”的双断言，而非直接删除测试。

### 4.4 内容与确认夹具

需求、PRD和方案使用现有 `test_requirements_prd_tools.py`、`solution_test_support.py` 的合法模板及版本绑定。A/B正文带不同哨兵；复制隔离用例故意保持相同编号与内容，保证不是靠内容差异拒绝。

方案正向用例使用已有明确标记的模拟正式确认夹具，同时验证无确认／过期／错误用途的负向。模拟确认只证明校验算法，不证明真实受信确认入口存在，不能写入业务样本。

UI夹具复用 `ui_test_support.py` 和 `test_ui_accept.py` 的候选/集合结构：按工具返回的 workspace_path 编辑 tree 和 candidate.json，经真正的检查工具取得 inspection_id 后接受。外部源提供最少完整的页面、设计和说明，不执行其脚本。

旧格式历史／候选／未闭合事务由旧版本工具在临时环境产生并记录来源。不要通过改受管摘要、路径或运行基线把损坏记录伪造成合法旧记录。

## 5. 公共操作约定与独立观测

### 5.1 MCP 调用链

每条实际工具调用仍带完整 `project_path`。先 initialize，再发 initialized 通知，再 tools/list／tools/call；按服务实际支持版本执行，不猜握手已完成。

| 操作 | 调用顺序与参数 |
| --- | --- |
| 新建 | `requirements_project_inspect`（只读）→明确的 `requirements_project_initialize`，提供名称、用途及路径；project_id仅在适用新建场景指定 |
| 需求保存 | `requirements_read_context`→`requirements_save_draft(content, read_id)` |
| PRD保存 | 读取当前需求/PRD→`requirements_save_prd_draft(content, read_id)`，随后按协议核对来源、结构与历史 |
| 补录 | 当前读取→`requirements_project_update_info(read_id, changes)`；变更后重新读取再保存 |
| 恢复/历史 | `include_recovery=true`；需求 `history_sha256`、PRD `prd_history_sha256` 使用各自实际历史摘要 |
| 方案 | `solution_read_context`→按需 `solution_inspect(target=candidate, content, profile)`→`solution_save_tech_spec_draft(read_id, content, profile)` |
| UI准备/接收 | `ui_read_context`→`ui_prepare_revision(read_id, request_id, mode)`→编辑候选→`ui_inspect(target=candidate, revision_id)`→`ui_accept_revision(revision_id, inspection_id, request_id, delete_paths)` |
| UI历史 | `ui_read_history`，随后以 mode=history 准备新候选，不能直接覆盖公开目录 |
| UI事务 | `ui_inspect(target=transaction, transaction_id)`→明确 `ui_recover_revision(transaction_id, request_id, action=resume或rollback)` |

工具的准确字段、返回形状与必填项以实际协议定义为准；新增 internal binding 不应成为可由模型提交的工具参数。

### 5.2 能力开关

需求默认3项只读；只开初始化为4项，只开保存为6项，两者都开为7项。方案默认2项，开保存3项。UI默认3项，开写6项。逐项检查名称集合，不能只比较数量；导入范围由独立 `--import-root` 提供。

外部 JSON 中的 authorized、binding、expected版本等未知授权字段应被拒绝；clientInfo 和材料自称权限不提供能力。仅保存工具开放也不能替代正式确认。

### 5.3 快照和错误判定

每次测试至少独立记录：相对路径集合、文件类型、普通文件SHA-256、软链目标；目录身份测试另记录dev/ino。不得为了快照跟随指向安装树外的软链。Git专用场景记录index、refs及真实Git状态。

区分公开成果、历史、候选/事务私有状态、配置和外部源。只读必须没有落盘副作用；写前拒绝通常要求原树不变，既有契约允许的读取凭据消费或内部事务证据需分别核对，不要求所有失败在任意阶段都字节零变化。

写结果采用原协议：saved、unchanged、not_written、unknown、saved_unverified 等；UI的 transaction_status 另行记录。进入内核后异常即使发生在首次公开替换前，也可能按原需求协议返回unknown，不强行统一成not_written。结构问题、工具保存成功和正式确认分别判断。

所有负向必须有“正向对照可达＋具体拒绝原因＋禁止副作用未发生”。只断言抛异常、返回非空或HTTP/JSON-RPC失败不足以通过；不得用过期凭据、缺能力或错误项目ID提前遮住本要验证的边界。

### 5.4 确定性竞争与权限

用 barrier、事件或现有failpoint精确放在检查后、取得锁后、首次替换前、写后复读前等位置，不依赖随机sleep碰撞。至少覆盖内核线程/进程间竞争和一个真实stdio写路径。

高权限环境无法形成真实权限拒绝时，mock只用于错误分类，真实权限子用例仍为BLOCKED。拒绝测试结束在finally恢复临时权限、关闭本用例子进程；不删除真实锁、不终止无关进程、不清理原业务目录。

## 7. PATH-01—40 逐项执行规格

每项以下列固定字段给出。执行时展开适用模式、角色和阶段的所有子场景；某一子场景未执行，母项不能标PASS。完整结构与结果字段另见配套JSON。

### PATH-01 原根之外初始化

阶段：P2；模式：E；层次：kernel+stdio。

**准备：** 在旧根 R 外准备已存在父目录 X；最终目录 X/new-a 不存在；初始化能力开放。

**操作：**

1. 只读 inspect X/new-a，记录建议编号。
2. 明确 initialize，同一次调用提供完整目录、名称和用途。
3. 读取项目并核对实际成员，再重复初始化一次。

**通过标准：**

- 只创建 X/new-a，不自动追加名称层，不在 R 创建目录。
- project.json 持久化实际编号；重复初始化不覆盖基础文件。
- 配置、旧映射和未选项目保持不变；不创建 Git 仓库。

**证据：** 最终目录成员、基础文件摘要、配置摘要、旧根快照、Git 写命令观测。

### PATH-02 多层中文与带空格路径

阶段：P2；模式：E；层次：kernel+stdio。

**准备：** 父目录 X/多级目录/客户 A 已存在，目标为其中的 采购 需求预测。

**操作：**

1. 以完整路径初始化，保存两版需求并读取历史。
2. 保存 PRD 并用三个角色读取该项目。
3. 另测 Unicode 名称和系统正常祖先别名的规范化。

**通过标准：**

- 路径和文本不截断、不错误拆分空格、不新增重复目录层。
- 三个角色返回同一规范目录与持久编号，历史位于该目录。

**证据：** 请求中的原路径、规范路径、编号、当前与历史正文摘要。

### PATH-03 不同父目录 A／B 交替调用

阶段：P2；模式：E；层次：kernel+stdio。

**准备：** A 位于 X，B 位于 Y；X、Y 均不在 R 内；A/B 使用不同哨兵正文。

**操作：**

1. 在同一需求服务依次读取 A、读取 B、保存 A、保存 B、再读 A。
2. 方案、UI 服务按 A→B→A 读取，保留各自读取记录。

**通过标准：**

- 每次返回匹配的路径、编号、正文；B 不覆盖 A 的服务上下文。
- 切换不修改配置，不需重新注册或重启 MCP。

**证据：** 逐调用 project_path 与返回身份、A/B 当前与历史快照、配置前后摘要。

### PATH-04 不同位置的同名目录

阶段：P2；模式：E；层次：kernel+stdio。

**准备：** X/演示与 Y/演示，两个合法项目。

**操作：**

1. 交替检查、读取并保存不同正文。
2. 检查服务缓存行为及返回身份，不只检查缓存变量名称。

**通过标准：**

- 不会因为 basename 相同混用实例、读取引用、历史或保存目标。

**证据：** 两个规范路径、保存目标、历史归属；必要的缓存观测。

### PATH-05 跨项目读取凭据保存

阶段：P2；模式：E／L0／L1；层次：kernel+stdio。

**准备：** A/B 都是合法项目，各自现有正文和摘要可核对。

**操作：**

1. 从 A 获取需求 read_id，带 B 路径调用需求保存、PRD 保存和补录。
2. 方案 A 的 read_id 用于 B 保存；UI read_id／inspection_id 分别跨项目调用。

**通过标准：**

## 9. 执行顺序和准确命令

所有命令从**唯一开发副本根目录**执行；编制时该副本及新测试还未创建，下列命令是实施后的执行入口。

```sh
python3 -B -m unittest discover -s fusion-runtime/tests -p 'test_project_binding.py'
python3 -B -m unittest discover -s fusion-runtime/tests -p 'test_requirements_*.py'
python3 -B -m unittest discover -s fusion-runtime/tests -p 'test_solution_*.py'
python3 -B -m unittest discover -s fusion-runtime/tests -p 'test_ui_*.py'
python3 -B -m unittest discover -s fusion-runtime/tests -p 'test_explicit_paths_stdio.py'
python3 -B -m unittest discover -s fusion-runtime/tests
```

P0先在未改造副本运行既有组，P1—P4按改动运行相关组，P5再聚合发现和真实进程主线。某批通过后没有新改动或未解决问题，不机械重复全量；发布副本因有独立来源/锁适配，仍要独立执行RELEASE-02。

保留每条命令真实退出码；日志可以重定向，但不能让tee等后续命令的成功掩盖测试失败。不从“Ran 0 tests”“OK (skipped=...)”推断功能通过。

### 9.1 真实进程的额外要求

使用服务支持的标准启动方式，从other-workdir启动。忽略非必要Python环境和用户包路径，检查实际模块 __file__；不能要求未承诺支持的入口统一使用 `-I`。stdout只读MCP协议，stderr独立留档；每次请求记录ID，限时等待后核对进程状态，不盲目重发写请求。

逐组合发现能力：需求3/4/6/7、方案2/3、UI3/6，并核对名称。E的两项目放不同父目录，L0/L1用R内合法项目。重启后原read_id／inspection_id必须失效；持久候选/历史/回执按原协议及新格式兼容规则检查。

CLI用例以真实 `--help` 确认新增参数位置，不提前把猜测的命令写成已通过。旧命令必须作为独立子进程执行；只用内部函数mock不能代替CLI兼容证据。

### 9.2 UI故障矩阵

| 注入位置／变化 | 必须观测的边界 |
| --- | --- |
| 固定前像后、激活前 | 公开目标未变化；可以在明确意图下关闭/回滚私有事务 |
| before_first_write | 检查凭据消费时机和已激活状态按原协议，不能盲目重试 |
| member_after:0 等部分成员后 | before/after混合，未知结果；resume补完或rollback精确恢复 |
| after_pointer | 当前指针可能已更新但写后核对未完，不冒充完整saved |
| after_saved_receipt | 已提交回执幂等重放，不启动第二次写入或错误允许回滚已提交版本 |
| 来源变化 | resume拒绝；本地完整前像rollback不覆盖来源新内容 |
| 目标为第三方字节 | 不当作before或after，恢复拒绝覆盖 |
| 根目录/父路径替换 | 准备、检查、接受、恢复均不能改绑另一对象 |
| 外部导入授权撤销 | 持久来源root不提供授权；本地rollback不需要额外外部读取 |
| 锁/项目索引事务存在 | 不自动删锁或接管其他事务；明确在途状态 |

优先复用现有测试failpoint，不为测试在MCP公开暴露注入参数。精确事件名以当前实现为准；新目录重验若需内部屏障，明确其测试用途，不降低生产分支保护。
