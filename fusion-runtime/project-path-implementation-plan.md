## 2. 本次交付与不变规则

目标示例：用户指定 `/完整位置/采购需求预测`，需求角色直接在该项目根目录初始化和保存；方案、UI 通过同一位置识别同一持久项目编号。切换项目只改变调用中的 `project_path`。

必须保持：

- `project_path` 指项目本身的绝对目录，不再自动拼接一层业务名。
- 每次 MCP 调用仍明确传路径；不增加进程级“当前项目”、全局项目注册中心或自动目录扫描。
- 只读检查不创建目录、登记身份、补写文件或修改配置。材料正文中的路径不自动成为操作目标。
- 新目录仅允许缺失的最终一级、或已经存在的空目录；父目录必须存在。非空未初始化目录不自动接管，损坏元数据不降级为新项目。
- 已有项目身份以合法 `project.json.project_id` 为准；目录名、旧映射和建议编号不得覆盖它。
- 保存继续受启动能力、读取凭据、版本、历史、写后复读及各角色业务前置条件约束。
- 不修改业务项目原来的初始化依赖、确认记录、正文或历史来适应新工具；项目搬迁不继承旧凭据。
- `expected_root` 只核对预期目录，不能单独作为显式定位入口或授权参数。
- 文档操作与 Git 建仓分开。合法项目位于另一仓库内，不应仅因此无法读取；Git 写操作继续执行专属条件。

本次不做：非空目录接管、自动搬迁、远端同步、图形设置页、公共基础物理拆包、通用 Git/MCP 新工具、正式确认签发或工作流引擎。

## 3. 配置和共享绑定契约

### 3.1 模式配置

继续采用配置 `schema_version=1`，增加 `project_path_mode`：

| 输入 | 必须实现的行为 |
| --- | --- |
| 缺少模式字段 | `legacy_rooted`，保持旧根目录与直接子目录规则 |
| `legacy_rooted` | 校验并使用 `projects_root`、`project_directories` |
| `explicit` | 根据本次完整路径绑定；不解析旧根目录是否存在，不用旧映射决定身份或目标 |
| 未知值、空值、布尔或非字符串 | 明确报配置错误，不回退或自动纠正 |

显式模式仍检查安装目录、方法软链、上游锁与受控加载来源。旧字段可留在配置中用于回退，但其旧路径失效、映射不适用于当前项目时不得阻断显式模式。服务运行中配置字节或模式变化，停止使用旧读取凭据，要求重新核对／重连；不要热切换已有实例。

新安装示例在文档完成后推荐 `explicit`；不改“字段缺失等于旧模式”的兼容约定。实际本机 `local.json` 到 P6 才修改。

### 3.2 新模块与依赖方向

新增 `requirements/file_tools/project_binding.py`。保持普通标准库模块，不依赖任何角色服务、客户端、模型或业务文件夹内代码。

推荐依赖顺序：

```text
check_foundation（配置、安装与方法校验）
    → project_binding（路径、最小身份与目录绑定）
    → project_init／requirements／project_info／recovery
    → 三个 MCP 接入层
```

`project_binding` 不反向导入 `project_init`，避免受控加载器循环。将项目 ID 的纯校验移到共享模块，`project_init.require_project_id` 保留兼容包装。完整初始化结构继续由 `project_init.load_project` 校验；共享模块取得合法编号不等于完整项目结构已经通过。

两个 `shared_loader.py` 的受控顺序在 `check_foundation` 之后、`project_init` 之前加载新模块，固定闭包从九文件变为十文件。同步修改对应来源记录和夹具，不从 cwd、旧 scripts 或业务目录补齐导入。

### 3.3 内部接口

建议采用不可变数据类，接口名称在 P1 固定后保持一致：

```python
bind_project(foundation, project_path, *, allow_uninitialized=False,
             requested_project_id=None, protected_roots=()) -> ProjectBinding
revalidate(binding, *, require_initialized=False) -> None
bind_initialized(binding) -> ProjectBinding
binding_fingerprint(binding) -> str
```

| 绑定字段 | 含义与限制 |
| --- | --- |
| `foundation`、`mode` | 当前已校验安装与目录模式 |
| `requested_path` | 首次收到的绝对路径拼写，用于发现父路径后来被改绑 |
| `root` | 首次规范化后的唯一实际项目路径 |
| `project_id`、`identity_source` | 建议身份／持久身份；已有元数据只能返回持久编号 |
| `state` | missing／empty／initialized／nonempty_uninitialized；非法元数据直接错误 |
| `parent_identity`、`root_identity` | 目录的设备号与 inode；根目录缺失时只固定已存在父目录 |
| `environment_fingerprint` | 配置、采用模块、方法与锁的运行基线；不包含密钥值或用户正文 |

不得只按项目编号缓存；缓存键采用规范路径，读取记录同时核对路径、编号、目录身份与运行基线。目录 mtime／ctime 会被正常写入改变，不作为目录替换的等价判据。元数据文件内容版本由既有版本机制检查，不把合法原子替换 `project.json` 误判为项目根目录替换。

新项目编号沿用现有规则：合法 ASCII 目录名可作为建议编号，其他目录按规范路径产生稳定建议编号；只在明确初始化成功后持久化。用户显式指定编号仅用于新建，同一路径已初始化且编号冲突时拒绝。不同目录可以持有相同编号，仍是不同操作对象，不建立全局唯一编号索引。

### 3.4 路径、身份和生命周期

1. MCP 层要求非空绝对路径字符串，拒绝 `..`、文件、项目根软链／断链及控制字符；不把 `~` 视为完整绝对路径。
2. 首次规范化可处理操作系统正常的祖先别名，例如 macOS 临时目录。解析后不得落入被保护目录；不能每次重新解析后悄悄接受另一目标。
3. 被保护集合至少包括当前 requirements、方案、UI 安装目录及上游方法目录；项目与这些位置相等、互相包含均拒绝。角色传入其他实际运行目录时加入集合。
4. 初始化缺失目录只允许最终一级缺失；固定父目录身份后排他创建。父路径缺失、父目录改变或创建竞争时停止，不递归创建未知链。
5. `project.json` 存在即核对其文件类型、JSON 结构、格式版本和编号；不可读、软链、非独立普通文件或损坏均不得回退为建议身份。
6. 每次工具入口、锁内实际写入之前、UI 每个阶段以及关键写后核对重验绑定。目录或父路径在检查点被替换时，停止后续业务写入。
7. 初始化完成只通过 `bind_initialized` 明确取得新持久绑定，清除该实例之前的读取引用。不能把外部出现的任意新元数据自动接受为初始化成功。
8. 文件锁协调遵守协议的调用，不阻止其他进程操作文件。保持既有原子替换与安全文件检查，不宣称凭一次 Path.resolve 就消除了所有文件系统竞争窗口。

### 3.5 下层 API 兼容

`project_init.context` 及沿用它的文件 API 增加内部可选关键字 `binding=None`，保留已有位置参数和 `expected_root`、`directory_name`：

- 传入绑定：重新校验绑定、项目编号和 `expected_root`；`directory_name` 若存在只作一致性检查，不再重建目标目录。
- 未传绑定且处于旧模式：走现有根目录定位规则。
- 未传绑定且处于显式模式：明确要求本次路径绑定；不从编号、旧映射、cwd 或 `expected_root` 猜目标。
- MCP 的外部参数不增加可提交 `binding`、`authorized` 或运行基线的字段；普通调用者不能用 JSON 伪造内部上下文。
- 保留旧 CLI；若显式模式使用文件工具 CLI，为其增加可选绝对 `--project-path` 并在入口建立绑定。缺少路径时报明确错误；旧模式不要求新增参数。

### 3.6 初始化依赖与准备计划

`creation_dependencies` 在显式模式要求当前绑定，保留初始化版本、来源摘要和上游锁，增加独立的初始化绑定记录，注明当时模式、路径和编号。它是创建时的历史事实，不是项目搬迁后的永久定位规则。

旧模式保持原字段语义；已有项目的 `dependencies` 不重写。初始化版本按实际接口变化明确递增，不冒用旧版本。

`prepare_creation`、`verify_prepared_creation`、`apply_prepared_creation` 不是当前 MCP 的主入口，但必须核对其兼容：显式模式传入当前受信绑定；准备数据中的路径不能自行提供访问授权。保留严格准备数据校验，不为省事放宽 `PREPARED_KEYS` 或忽略依赖差异。原旧模式调用继续按旧契约工作。

## 11. 回退与停止条件

**临时回旧模式**：配置改为 `legacy_rooted`、保留原根目录和映射、重载服务。范围外项目留在原位置，旧模式无法访问不等于文件丢失；旧读取引用失效后重新读取。

**恢复旧工具**：按安装备份清单一起恢复代码、角色说明、来源采用记录和配置，重新加载同一套旧基线。不能只恢复 Python 或只改 SOURCES。新建业务项目和业务历史不随回退删除或覆盖。

遇到相关基线被另一写入者改变、未知来源漂移、无法保证目录重验、实际写入范围超出清单、需要新增正式确认入口或非空接管时，停止该受影响动作，保留可核实结果并报告具体差异。普通实现选择、可修复测试失败、无关工作区差异不触发额外审批。

无论停在哪批，均说明已改什么、实际检查、未验部分和下一步；不得把“源码完成”“350 项旧记录”“服务启动”写成完整业务验收完成。
