## 1. 建设目标与首版范围

### 1.1 要解决的问题

需求能力已经能够讨论需求、形成和保存轻量需求／PRD，并在恢复时识别来源关系和确认状态。接下来的方案能力需要承接这些结论，回答：

1. 系统通过哪些模块、服务、模型和工具实现需求？
2. 输入、输出、数据、状态和接口怎样衔接？
3. 成功、失败、超时、重复操作及恢复分别怎样处理？
4. 哪些技术选择需要用户决定，哪些由方案角色自行安排？
5. 每项 REQ／AC 由哪里实现，后续如何验证？
6. 哪些结论已有依据，哪些只是合理推断，哪些仍需实验或外部条件？

首版交付的核心是**有依据、可追踪、行为明确的实现契约**。七层文档承载设计结论，不能用章节完整代替设计正确。

### 1.3 首版建设范围

- 可通过显式指定主文档，在 Cursor、Codex 等环境中独立开展方案讨论。
- 读取实际项目、PRD、来源关系、项目选择、有效确认和已有方案。
- 复用七层方法、体验走查和有限查证，逐步形成或修改工程方案。
- 按请求保存 `docs/tech-spec.md` Draft，记录输入版本，保留旧版并复读。
- 检查 REQ／AC 覆盖、引用、基本结构及输入版本关系。
- 支持局部修改、冲突处理、历史读取和新会话恢复。
- 明确回报当前成果、未决项、证据范围和后续接收所需条件。
- 方法入口与权威工程模板归属方案目录，日常工具运行不再依赖旧 buzz-develop-helper 目录；复用 requirements 的实际依赖明确记录和验证。

### 1.4 首版暂不建设

- 客户沟通版 `solution.md` 的模板、生成与保存工具。
- 统一主 Agent、自动意图路由、多角色调度和消息中转。
- UI／原型制作、Feature／Task 拆分、业务代码开发和独立业务测试。
- 新的正式确认签发器、成果登记写入及自动交接发送。
- 模型效果、性能、成本的通用实验平台，及自动安装／运行验证环境。
- Buzz／ACP 全链路、远端同步、跨机器配置和多用户鉴权服务。
- 新建方案业务状态机、数据库或后台等待服务。

需要保留设计理由、用户可见后果、外部依赖、假设和待验证项。这些本来就是工程方案的必要内容，也能为将来的客户表达提供依据；首版不因此额外维护第二份方案。

### 1.5 独立性的具体范围

| 独立性 | 首版目标 |
| --- | --- |
| 独立使用方案角色 | 不依赖主 Agent，不要求先启动需求对话；直接使用已有材料和成果 |
| 不依赖旧融合目录日常运行 | 正常角色必读方法／模板、方案工具及正式测试不加载 buzz-develop-helper；旧目录只保留为迁移来源和历史依据 |
| 不依赖 requirements 目录运行 | 首版不承诺；明确依赖其本地基础模块、配置结构和锁定基线 |

“方案有自己的软链”“能独立对话”“可单独分发运行”分别判定。将来需要脱离 requirements 时，再迁移最小依赖闭包并验证，不在本轮预建通用平台或复制完整需求模块。

#### 2.4.5 配置、规范和正式确认依赖

- **配置根**：使用 requirements 目录；local.example.json 有 schema_version、upstream_root、projects_root、project_directories，当前真实 local.json 缺失。项目目录绑定还需 Git 只读边界检查。步骤 5 可用隔离临时配置；步骤 8 再按明确范围准备真实映射和客户端条目。本步未读取或复制旧本机配置、未核查用户全局客户端配置。
- **规范解析**：project_info.specification_root 从配置的 upstream_root 解析 harness-core/specification；resolve_specification(None) 返回 not_used，字符串只接受规范库内单层、非软链目录；report 区分字段缺失、null 和非法值。当前上游有 default 集（14 份规则及库索引），本步只核对索引、路径和内容指纹，不为具体业务选择该集。
- **规范正文**：resolve_specification 只检查集目录，不读取规则正文，也不保证未来所引用每个文件可读；方案按类型和设计范围从选定集内定向读取。上游规范索引的 .sdd/project.json／Planner 表述，在融合层仍按根 project.json 和角色边界适配，CLI 不隐式套 Web 架构。
- **确认读依赖**：project.json 内 artifact_registry、docs/decisions.md 受管记录，以及登记中各版本指向的实际文件／清单／成员和记录快照。validate_registry 会遍历整个登记，非 PRD 登记内容损坏也可能使核验无效；保存的保护集合不能预设只有 PRD＋decisions。
- **确认条件**：本项目、当前 PRD SHA、“形成技术方案”、无 open_items、登记反向确认引用和快照内容一致；当前需求核验明确区分 valid／outdated／invalid／missing／unavailable。旧品牌记录标记与 schema 兼容，不重新签发身份。
- **引用保护**：需求 MCP 只把 project.json、README、PRD、轻量需求四份文件计入 read_id，recovery 的方案／确认是附加材料。recovery.read 的变化检测也没有覆盖全部登记内容与快照，不能作为方案完整保存屏障。
- **确认写入缺口**：当前需求 MCP 的七项工具不含正式确认或登记写入；旧 Main 模块虽存在，但被选定首版依赖排除。步骤 4 需核实可用受信生产入口或现有有效记录的取得方式；临时夹具可支持工具测试，不证明真实入口完成。不为补这个条件先建设完整主 Agent。
- **配置安装差异**：现有 configure_cursor.build_entry 固定 requirements 名称、cursor_mcp.py，并加入 allow-initialize／allow-save。只复用配置处理算法，方案不得调用它直接生成需求条目或开放初始化权限；服务名称和能力在步骤 4 固定。

这些条件是后续运行或整链验收的依赖，不构成步骤 1 未完成；本步要求把它们准确查清，不要求已创建未来配置和工具。

| 上游或旧融合行为 | 首版适配 | 理由 |
| --- | --- | --- |
| 由主智能体固定派发 solution-designer 子智能体 | 显式加载主文档即可由当前 Agent 承担方案职责；未来主 Agent 也可调用 | 角色能力不依赖先建设统一主 Agent |
| 关键问题由主智能体转达 | 独立使用时直接与用户讨论；被调用时按接入方式返回 | 保留设计方法，减少不必要的组织依赖 |
| 直接编辑 tech-spec 并改成 Confirmed | 通过受控工具保存 Draft；正式确认由单独能力承担 | 版本与确认依据可核对 |
| 方案阶段直接回写 PRD／AC | 产生受影响项和变更建议，由需求能力按请求处理 | 防止技术方案静默改变业务承诺 |
| 技术时序细化在 PRD 中 | 采用现有单元 03 的分工：业务图归 PRD，技术图归 tech-spec | 减少重复维护和漂移 |
| 重要取舍写 decisions.md | 首版在 tech-spec 中记录设计理由和取舍；只读正式确认记录 | 当前 decisions.md 含受管确认数据，方案角色不写入 |
| 确认后自动进入 B／Plan | 回报候选版本与建议用途后结束 | 下游启动与方案完成分别处理 |
| 旧 Buzz 可信上下文是固定入口 | 本地单用户 MCP 使用配置范围、显式项目选择和能力开关；未来宿主身份另适配 | 不把平台绑定写进核心方法 |
| 角色经旧共享目录或兄弟角色定位方法 | 建立方案自身 methods 软链，直接指向唯一上游原文 | 保留相邻资料的原始相对关系，减少角色方法路径耦合 |
| 工程模板直接引用旧融合 capability | 本地复制后由方案目录维护唯一模板 | 迁移来源与日常权威模板分开，旧模板继续服务原使用方 |
| 方案内核直接导入旧 scripts 的确认／登记模块 | 适配为对 requirements 本地只读校验的明确依赖 | 避免重新带入 Main 写入闭包，不重复实现确认格式 |

### 3.3 暂不改变的工程保存门槛

现有单元 03 和方案保存内核要求：当前 PRD 有可核验的“形成技术方案”用途确认，才允许保存工程 tech-spec。首版沿用此要求。

缺少确认时允许读取、检查、讨论候选及保留在当前对话中的预研结论；不通过普通编辑工具保存工程方案，也不伪造登记或确认记录。若未来希望允许“未经正式确认的预研草稿落盘”，需单独修改契约、元数据和工具规则，不能在实施时默默放开。

### 3.4 新增建议及其范围

本方案已形成角色主文档和文件操作约定；继续建设本地方法／模板、独立 MCP 薄入口、来源记录及验收。首版依赖 requirements 本地基础能力，不在此依赖之上另立通用平台。八步流程将设计试用放在工具实现之前，客户端真实接入放在代码验收之后；不增加业务阶段，不新增工程权威成果，不放宽正式确认或下游启动权限。

本文不作为 `fusion-design/03-方案能力.md` 的自动替代文档。实施时若发现规则冲突，列出具体差异并按当前授权范围修改；不能仅凭本文新建日期推定旧契约全部失效。

## 4. 职责与独立使用方式

### 4.1 各方职责

| 对象 | 职责 |
| --- | --- |
| 用户 | 提供实际目标与约束，决定影响业务结果或重要代价的取舍，表达保存或后续使用意图 |
| Solution Designer | 恢复材料、设计实现路径、查证关键事实、组织取舍、修改候选、请求工具并解释结果 |
| 方法与模板 | 提供思考范围、设计深度和交付标准，不执行流程或产生权限 |
| MCP／文件内核 | 核对目录、版本、确认记录，执行限定文件操作、历史和复读 |
| 需求能力 | 维护用户结果、业务规则、REQ／AC 和业务图；处理方案反馈出的业务变化 |
| 正式确认／登记能力 | 按准确版本和用途记录用户决定；当前接入与权限单独验收 |
| 未来主 Agent | 选择能力、协调材料和交接、核对整体进度；不重复维护方案分析方法 |

### 4.2 入口体验

用户可以表达：“使用方案角色，基于这个项目的 PRD 设计本次工程方案”“继续上次方案”“只修改失败恢复部分并保存”。不要求用户填写内部 SHA、read_id、确认 ID、阶段代码或 JSON。

仅讨论时无需创建项目；需要读取既有成果或保存时，核对用户选定的项目。已有项目复用现有目录和身份，不重建、不搬迁、不扫描其他项目。

首版采用显式入口。工具说明可以提示主文档位置，但发现工具、看到路径或读取项目文件，不等于已经读取和正确采用方法。自动触发及统一路由后续单独建设。

## 5. 输入门槛与分流

### 5.1 按用途核对输入

| 输入 | 讨论用途 | 工程保存用途 |
| --- | --- | --- |
| 本轮目标和范围 | 必须清楚 | 必须清楚，包含局部／完整范围 |
| 项目身份与目录 | 可在纯讨论时缺省 | 必须由接入层核对 |
| 业务材料 | 足以支撑当前问题即可 | 读取当前完整 PRD 及相关需求来源 |
| 稳定 REQ／AC | 缺少时说明工程追踪限制 | 必需，且关键验收信息可用 |
| 项目类型、平台、规范 | 采用已知信息 | 继承项目记录；规范 null 与缺失分开 |
| PRD 来源关系 | 有材料时核对 | 来源变化或缺失记录应明确处理 |
| PRD 用途确认 | 不阻止讨论 | 必须有效，精确绑定当前 PRD 和“形成技术方案” |
| 已有方案与其他资料 | 按影响范围读取 | 修改时必须读取实际目标与基线 |

规范明确为 null 时不加载规范集；未记录时不推定 default。只有缺失选择影响本轮设计时才定向补问，不能要求用户重选全部初始化信息。

### 5.2 分流规则

| 情况 | 行为与结果 |
| --- | --- |
| 只有轻量需求 | 可以讨论实现思路和需求缺口；工程保存前补齐 PRD／AC，不将预研称为开发基线 |
| PRD 缺失或不可读 | 区分缺失和读取失败，说明受影响部分，不从聊天摘要重造已存文件 |
| PRD 有关键业务歧义 | 返回具体 REQ／AC 的问题及候选，不重跑整套访谈；独立部分可继续 |
| PRD 确认 missing／outdated／invalid／unavailable | 展示原因和补齐条件；可讨论，不保存工程方案 |
| 需求已变化，PRD 尚未同步 | 比较相关差异；不能把旧 PRD 的有效确认扩大到新增业务要求 |
| 已有 tech-spec 绑定旧 PRD | 标出变化与受影响设计，按新基线修订，不仅刷新元数据 |
| 仅外部协议、效果或性能待核实 | 定向查证或提出最小验证；说明哪些设计可以继续，哪些用途受阻 |
| 只有普通内部实现细节未定 | 由方案角色在现有约束内安排，并保留必要理由 |

需求到 PRD 的来源核对由 Agent 与读取工具共同提供证据。文件摘要匹配只能证明版本关系，不能证明 PRD 忠实表达全部需求。

## 6. 对话与设计流程

### 6.1 一次方案工作的顺序

1. **理解本轮用途**：新方案、继续、局部修改、审阅或保存。
2. **恢复实际基线**：读取相关正文、项目选择、来源、确认和已有方案，概括已明确内容及变化。
3. **串起端到端链路**：从用户输入到最终结果，列实际参与者、数据、状态和关键失败。
4. **识别决定顺序**：先解决会影响后续设计的关键问题，独立部分并行思考但不自行派发角色。
5. **形成取舍与建议**：说明具体情境、选项、用户后果、推荐及代价，每轮聚焦少量相关问题。
6. **按需查证**：核对外部能力、协议和限制；将证据带回当前设计。
7. **补齐七层及追踪**：更新接口、数据、算法、异常和技术时序，逐项落实 REQ／AC。
8. **检查候选**：走查成功、耗时、失败和再次操作，区分设计缺口与真实验证缺口。
9. **按请求保存**：核对准确候选和读取基线，调用受控工具并复核实际结果。
10. **报告并结束**：说明版本、覆盖、未决项、未验证范围及建议用途；不自动启动 UI／Planner。

这是 Agent 的工作方法，不据此建设一轮一次调用的程序 Workflow，也不要求每轮输出协议 JSON。

### 6.2 哪些问题交给用户

会明显改变等待与操作方式、结果质量、数据留存、费用、权限、恢复能力或既有业务承诺的选择需要讨论。已有明确选择直接沿用；普通命名、内部函数划分和未改变契约的实现细节由角色决定。

例如，“超时后后台继续执行”会影响重试、重复结果和费用，应明确；某个纯内部辅助函数如何命名，不构成用户决策。

### 6.3 业务变化的返回闭环

当设计发现必须改变业务结果时，输出：受影响 REQ／AC、变化原因、候选行为、对成功／失败结果的影响，以及能继续设计的独立部分。

用户接受业务变化后，由需求能力按请求同步轻量需求和 PRD；重新读取新版，核对新的确认状态，再继续工程保存。各文件分别写入，不能承诺需求、PRD、方案原子同步。

在变化尚未同步时，候选必须标注待同步和受影响项；不能使用旧确认保存声称实现新业务承诺的方案。

## 7. 工程成果与深度

### 7.1 唯一工程方案

业务项目中的标准成果为 `<项目目录>/docs/tech-spec.md`。首版不新增第二份工程权威方案，不将建设计划、测试记录或聊天摘要当成业务设计。

| 配置 | 采用条件 | 表达要求 |
| --- | --- | --- |
| Lite | 简单脚本、CLI、小型自动化或边界清楚的单服务改动 | 核对七层问题，简写不适用部分，不虚构前端、HTTP API、数据库或队列 |
| Standard | Web／客户端、多模块或多个系统集成 | 明确完整边界、接口、数据、状态、异常、权限及联调条件 |
| AI | 包含模型、Agent、提示词、工具或非确定性处理 | 在适用工程部分之外，明确模型职责、输出约束、评估、工具边界、回退和人工复核 |

小型 AI 脚本仍使用 AI 配置，但不强造多服务架构。当前旧检查器按章节编号检查 Lite 文档；首版模板可保持统一编号并简写，避免文档允许合并而工具机械拒绝的矛盾。若决定支持合并章节，应同时调整检查器并验证。

### 7.2 正文结构

| 章节 | 必须回答的内容 |
| --- | --- |
| 0 基线与用途 | 项目、本次范围、输入材料与版本、配置理由、建议用途和明确不覆盖 |
| 1 用户结果与覆盖范围 | 引用 REQ／AC，概括输入、处理、成功和关键失败结果 |
| 2 系统边界与接口 | 模块职责、真实接口／命令／事件、请求响应、权限和重复操作约定 |
| 3 数据与生命周期 | 字段类型、校验、流转、存储、敏感性、过期与清理 |
| 4 模型、提示词与工具 | 职责、选型依据、输入输出、解析校验、工具权限、评估和回退；无 AI 说明原因 |
| 5 算法、状态与体验影响 | 实际处理步骤、状态转换、停止条件，以及等待、质量、费用与恢复后果 |
| 6 异常、重试与恢复 | 失败触发、错误／状态、用户反馈、可重试范围、重复副作用和资源清理 |
| 7 目录、运行与验证条件 | 文件职责、依赖、运行方式、配置字段、外部条件及验证方法 |
| 8 技术时序 | 真实参与者、调用方向、同步／异步／流式、关键异常与反馈 |
| 9 依据、假设与可行性 | 事实、来源、推断、验证范围、未证事项及影响 |
| 10 取舍与未决项 | 已决定、待决定、暂不阻塞，包含选择理由和复议条件 |
| 11 REQ／AC 覆盖表 | 实现位置、成功／失败路径、验证方法与覆盖状态 |
| 12 变更与建议下一步 | 相对旧版变化、影响范围、建议用途与实际保存状态 |

使用既有统一模板作为起点，必要的融合说明在本地主文档和模板维护；不复制上游七层方法全文。

### 7.3 覆盖关系

覆盖表沿用：REQ、AC、实现设计／API、成功路径、失败路径、验证方式、当前状态。

- `covered`：已给出可定位的实现设计与验证方法；不代表实现已完成或 AC 已实测通过。
- `not_applicable`：明确理由和适用范围；不能用来跳过仍必须实现的验收。
- `open`：存在待决定或待补证据，应说明影响与后续条件。
- `blocked`：存在明确阻塞，需指明原因和解除条件。

一个 AC 可由多个设计项覆盖，一个设计项也可承接多个 AC。没有网络 API 的验收指向真实命令、模块或设计章节，不强造 API 编号。

完整方案逐项说明当前 PRD 的 AC；局部修改沿用既有方案完整覆盖表，只更新受影响内容。首次仅设计局部范围时，未覆盖 AC 明确为本次范围外并标 open，不能宣称全 PRD 可进入开发；未来确认范围必须相应收窄。更细的范围元数据如需机器强制，列入实施契约，不靠文字声称已支持。

### 7.4 AI 设计的特别要求

- 区分模型完成的判断与代码执行的校验／副作用，不把所有处理笼统归为“调用模型”。
- 提示词至少表达职责、输入、输出结构、约束和异常处理；位置和版本方式明确。
- Agent 场景描述工具观察如何回传、怎样据结果继续、修复、停止或交给人工。
- 对拒绝、结构错误、内容不完整、工具失败和重复副作用给出处理路径。
- 明确评估样例类型与验证方法；未实测质量阈值标为目标或待验证，不写成保证。
- 价格、模型能力、上下文限制等采用当前可靠依据；没有依据时保持未知。

## 8. 依据、取舍与验证

### 8.1 事实与可行性分别记录

每项关键结论区分项目事实、外部事实、用户决定、假设、建议或未知。可行性继续采用 verified／reasoned／unknown／blocked，并同时注明证据类型和适用范围。

读到官方协议，可以证明协议所述接口或限制；不能因此宣称本项目已联通、性能达标或模型效果可用。实测结果必须记录测试对象、条件、版本和实际结果。

建议依据表包含：结论、性质、来源／版本／访问日期、证据范围、可行性状态、影响的设计／AC、验证方法与复议条件。低风险内容可简写，不为每条普通实现安排单独建档。

### 8.2 调研的两类用途

- 产品定位、功能取舍或交互需要参考时，按需读取上游 R，形成有限产品调研结论。
- 工程协议、模型限制或运行条件需要核实时，定向查阅官方资料或项目源码；不要求所有技术查证套用竞品研究结构。

二者共用来源、访问日期和证据边界要求。只有搜索摘要时注明摘要范围；推断与本项目决定分开；没有找到资料不能直接写成“不支持”。调研默认融入方案，独立研究报告按明确请求形成。

### 8.3 最小验证

方案角色可以提出验证目标、最小输入、执行条件、判定标准和预期影响。仅有设计授权时，不自行安装依赖、修改业务代码或发起付费调用。

已有明确授权和可用环境支持的验证，按该授权执行并记录范围；缺少凭据只阻塞相关真实验证，不能阻塞所有独立设计，也不能用 Mock 结果替代真实联调。

## 10. MCP 与文件操作设计

### 10.1 最小工具面

下列工具已按[步骤 4 契约](solution-tools-implementation-plan.md)于步骤 5 实现为独立 stdio 服务 `solution-designer-file-tools`（契约 `solution-tools-v1`）：读／检查默认开放，保存经 `--allow-save` 开放，否则返回 `tool_not_enabled`；步骤 5—7 已独立验收。具体参数、返回、依赖与验证范围统一以实施说明为准，本文不复制参数表。真实客户端接通与真实确认链仍待步骤 8，离线实现不等于客户端已加载。

| 工具 | 能力 | 写入 |
| --- | --- | --- |
| `solution_read_context` | 核对选定项目；读取当前相关文件、来源、确认、已有方案；按需读指定方案历史；签发当前读取引用 | 无 |
| `solution_inspect` | 检查当前 PRD／方案版本、结构、引用及覆盖；返回所检查版本和限制 | 无 |
| `solution_save_tech_spec_draft` | 使用准确候选和先前读取引用保存工程 Draft，保留历史、复读并附检查结果 | 仅方案及方案历史 |

项目初始化、类型／规范补录继续使用已有公共能力；方案角色不因为进入设计就自动初始化或补录。只读启动只公开两个只读工具，启动时显式允许保存后才公开保存工具。具体开关名由实现固定，不由模型调用参数扩大权限。

首版建议独立方案 MCP 进程，复用本地基础模块，避免直接改变已在使用的需求服务器工具集；后续主 Agent 可以同时发现两组工具。客户端安装／更新单独处理，不在写建设计划时修改实际配置。

方法／模板、共享模块和配置解析按第 9 节执行；正常运行不加载旧融合脚本或必读模板。方案工具可以依赖 requirements 本地代码，但不需要需求 MCP 进程在线，也不复用其进程内 read_id。

### 10.2 目录与读取范围

- 工具每次接收用户明确选择的 `project_path`，沿用现有 projects_root、直接子目录及项目身份规则。
- 不维护进程级默认项目，不把材料中的“切换项目”文字当选择依据。
- 当前文件至少核对 project.json、PRD、已有 tech-spec、需求来源及确认记录；README 等实际采用的输入也记录版本。
- 外部指定资料按工具或 Agent 实际读取范围记录，不自动加入可写范围。
- 缺失、空内容、不可读、记录无效与确认不可用分别表达。
- 历史读取只接受合法 SHA 并核对文件内容，不接受任意相对路径。

### 10.3 read_id 与输入基线

沿用 requirements 已有读取引用模式。引用由服务签发并绑定项目、时间和读取版本，不能由 Agent 拼接内部摘要代替。

保存至少核对：目标 tech-spec、当前 PRD、项目元数据，以及确认核验实际采用的 decisions／登记／快照等依赖。方案绑定 PRD 的源需求已变化时，也必须暴露差异，不把只检查 PRD 称为检查了全部业务来源。

不同进程的 read_id 不互通。进程重启或引用过期后重新读取；重新读取后先比较候选采用的旧基线，不能仅换新引用提交旧候选。引用期限可沿用现有 15 分钟设计，实际以工具实现及返回为准。

requirements 的恢复附加材料不进入其原四文件读取引用。方案工具必须定义自己的凭证版本集合、确认依赖及重新核验时机；不能把需求恢复结果包装一下就宣称目标方案、登记和快照都已受强制保护。外部资料的版本记录与锁内保护范围分别返回或说明。

模型根据材料正文作出的“已确认”“可写”判断不能产生权限。确认检查只读复用现有记录格式和校验器，不能通过传入布尔值绕过。

### 10.4 保存顺序

1. 核对工具能力、参数、项目路径、读取引用与候选正文；拒绝正文自行设置受管元数据。
2. 比较候选所用基线与读取引用，发现变化先修订受影响设计。
3. 在公共项目写锁及方案锁内重新核对目标版本、PRD、必要来源和确认依赖。
4. 核验当前 PRD 结构与精确用途确认，确认记录与登记快照满足当前契约。
5. 由工具生成 Draft、profile、PRD 摘要和确认引用等元数据；规范信息按项目继承并明确记录。
6. 内容确实不变时返回 unchanged，不制造新历史。
7. 保存旧目标到 `docs/tech-spec-history/<旧版摘要>.md`；已存在时核对实际摘要。
8. 临时文件写入并原子替换目标，释放锁和清理临时文件。
9. 复读目标，核对精确内容、元数据、历史和相关输入版本；独立运行结构检查。
10. 返回实际结果、读取引用消费情况、准确版本和结构问题，不自动登记、确认或启动下游。

锁和单文件原子替换不等于跨文件原子快照。对不遵守公共锁的外部修改，实施时应增加必要的写前／写后版本检查并如实报告剩余窗口；不得宣称所有来源全程原子一致。

### 10.5 写入结果

| write_outcome | 含义与后续动作 |
| --- | --- |
| `saved` | 已写入且写后核对通过；仍为 Draft |
| `unchanged` | 与预期结果完全相同，没有重写目标或新增历史 |
| `not_written` | 可以确定目标未写入；说明参数、能力、版本或确认等失败原因 |
| `unknown` | 无法确定是否写入；先读当前目标与历史，不盲目重试 |
| `saved_unverified` | 已发生写入，但指定写后核对失败；返回失败检查和实际可知信息，先核对再处理 |

进入可能发生写入的内核前消费一次读取引用；预检查拒绝是否消费需与 requirements 的实际规则保持一致并明确返回。结构检查失败与写入结果分开：允许保存有明确 open／blocked 的 Draft，不能因已保存就宣称结构通过。

### 10.6 客户端接入与配置变更

步骤 4 固定方案服务名称、启动命令、明确的 foundation 和能力开关，说明如何提供主文档与操作约定的定位；工具发现不能代替实际方法读取。首版新增方案服务，不直接替换或删除现有 requirements 服务，也不要求需求服务先启动。

配置辅助能力先在显式临时路径预览与测试：核对准确条目和配置版本，保留其他服务器及设置；目标条目同名但不同、目录软链、并发修改或备份失败时停止受影响写入。已有配置需更新时保留可核对备份，回退只处理匹配条目，不覆盖其他用户修改。

真实共享 local.json 的准备、客户端配置应用和服务重载属于步骤 8 的准确操作范围，已有明确授权则继续执行，不因本计划重问；仅授权代码或文档时不自动切换客户端。服务重启后旧 read_id 失效，必须重新读取。客户端配置与代码可用性、真实文件调用和正式确认链分别记录。

## 11. 检查能力的范围

### 11.1 首版机器检查

- 必需元数据、配置值、Draft 标记和绑定 PRD 版本。
- PRD 的 REQ／AC 定义、重复编号及方案中的未知引用。
- 七层及对应配置的必要正文结构。
- 覆盖表存在、列可解析、状态合法及 AC 是否有表内对应项。
- covered 行是否包含实现位置、成功／关键失败说明和验证方法。
- 明确不适用项是否具有理由，关键未决项是否被错误算作完成。
- AI 必需字段与技术时序标记，实际可检查范围按解析器实现报告。
- 确认状态、来源变化和检查期间观察到的版本变化。

旧检查器主要采用正则、章节编号和关键词。实施时应核对定义与引用、REQ／AC 归属、空表、多 AC 行及 Markdown 表格转义等问题；仅在首版真实用法需要时补齐解析，不把关键词存在宣称为语义正确。

### 11.2 仍需 Agent 或人工走查

- 接口请求响应是否真的能衔接，数据与状态是否存在矛盾。
- 算法是否落实了业务含义，失败后重试是否会重复执行副作用。
- 技术时序是否走完成功、空结果、失败、重试再失败等关键分支。
- 模型与外部能力是否有足够依据，限制是否被正确解释。
- 用户选择是否被准确继承，方案是否偷偷扩大范围或改变 AC。

图表有可用预览时进行渲染核对；只有源码检查时明示。首版不为绘图自动安装工具。

## 12. 修改、历史与恢复

### 12.1 修改

辨明用户是在补充事实、提出建议、作出选择还是要求替换。只更新受影响设计，保持其他有效结论和既有编号。用户说“修改并保存”包含本次修改的保存请求，不需要再问执行顺序；普通回答或审阅不自动变成保存请求。

PRD 变化时先比较 REQ／AC、范围和业务图，再定位接口、数据、异常、技术时序、依据表及覆盖表。纯内部实现变化不反向改业务需求。

### 12.2 历史

保存原始旧文件及其完整元数据，以真实字节计算摘要。历史读取核对文件名与内容摘要，历史冲突不覆盖。正确重试和 unchanged 不额外制造历史。

恢复旧版必须由用户明确请求，读出旧版后形成新候选，重新核对当前 PRD 与确认，再按正常保存链处理。历史不是通用 Git 回滚，也不恢复旧版确认的有效性。

### 12.3 新会话恢复

新会话实际读取主文档、适用方法、项目与成果，恢复：本轮范围、方案版本、绑定 PRD、来源关系、有效选择、关键设计理由、待决定／待验证项、上次实际保存状态和下一步。

未保存候选没有明确保留方式时，不承诺自动恢复。方案中的“用户已选择某项设计”只是设计记录，不能替代正式确认能力对整个成果版本与用途的核验。

恢复不会自动创建项目、更新规范、补写确认、保存方案或启动下游。

## 13. 完成与工程衔接标准

### 13.1 三种完成结论

| 结论 | 标准 | 可以声称什么 |
| --- | --- | --- |
| 本轮讨论完成 | 当前问题得到回答，候选、依据、未决项和保存状态清楚 | 已完成本次讨论／候选整理 |
| 工程方案 Draft 完成 | 当前范围设计和覆盖关系明确，无未标出的冲突；open／blocked 及验证条件完整披露 | 已形成可评审的工程方案草稿 |
| 可作为指定下游的工程基线 | 指定范围的关键契约完整，阻塞该用途的未决项为零，必要证据具备；准确版本已按用途确认，接收者可读取核对 | 可用于明确授权的 UI／Planner 或后续工程用途 |

首版目标是使方案具备成为开发输入的内容质量和工具可靠性；它不等于在首版同时建成全部下游。没有正式确认写入的真实接入证据时，可以完成角色和 Draft 工具验收，但“真实需求确认 → 工程保存 → 下游采用”仍须标待验。

### 13.2 下游交接内容

回报项目、方案路径与完整摘要、profile、本次范围、采用 PRD 与来源版本、PRD 确认引用、REQ／AC 覆盖状态、重要设计选择、阻塞项、待验证项、运行条件和建议用途。

### 建设顺序说明

步骤 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8。设计能力试用先于工具实现，工具实现后反向校准文档；正式确认链的依赖在步骤 4 就明确，真实采用在步骤 8 补验。步骤 1 的剩余依赖核对与步骤 2 模板整理可在不冲突时衔接开展，但不跳过退出条件。

方案讨论与工具开发不必等待需求侧所有研究缺口解决；具体业务样例的 PRD 质量和有效确认，会阻塞以它为输入的正向工程验收。代码及隔离运行可用临时配置和测试夹具验证，不能替代真实客户端／用户确认。完成状态分为文档已建立、案例试用通过、工具开发自验、代码独立验收、真实客户端通过及确认整链通过，不压成一个“已完成”。

实际实施按小步完成并核对退出条件，不预设大量轮次、不为每步新增同类报告。统一主 Agent、客户表达和自动路由在首版验收后按需求进入。
