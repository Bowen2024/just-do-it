## 1. 目标、依据和使用方式

交付独立的本机 stdio MCP 文件服务，使临时项目实际完成：

读取 → 准备候选 → 使用普通编辑工具修改候选 → 检查 → 受控接收 → 复读 → 查询历史。

同一实现必须拒绝越界、输入变化、候选变化、当前成果冲突及未获准覆盖，不以成功路径能运行代替保护验证。文件接收只证明文件集合保存，不证明业务、视觉、浏览器、正式确认或工程放行通过。

## 4. 5A：固定依赖和只读能力

### S5-A1：受控加载器与运行基线

依赖：S5-00。交付：`shared_loader.py` 与对应隔离测试。

1. 实现必填 `--foundation` 的普通绝对目录检查，从其 `file_tools` 显式加载九文件；使用 UI 专属别名包，不使用 cwd、同名诱导模块或旧 scripts 回退。
2. 按采用摘要核对文件，再调用公开基础能力核对配置、上游锁和双方法入口真实目标。
3. 建立启动时运行基线，并在每次工具调用复核。强制范围按契约第 2.2 节：角色、文件约定、模板、采用源码、必要配置／方法／锁；不将建设进度、测试报告或整个 SOURCES 的字节作为代码基线。
4. 将实现后新增源码的采用摘要明确记录在 SOURCES 中的运行源码记录；字段结构在实现报告中说明。摘要不匹配停止调用，不能通过每次启动自动重写记录取得通过。
5. 加载失败／基线变化返回契约错误，不热换配置和代码；不生成字节码或修改基础目录。

退出依据：T01—T03 对应的实际程序场景通过；新进程中可确认每个共享模块的真实加载路径；缺失和变更来源均被拒绝。

### S5-A2：统一校验、项目绑定、描述和凭证

依赖：A1。交付：`context.py` 的基础能力和公共响应封装。

1. 参数按六工具 schema 严格验证：未知字段、错误类型、条件字段组合、非法 ID／摘要拒绝；bool 不当整数。
2. 显式绑定 `projects_root` 的直接普通子项目，继承 project.json 和中文目录内部 ID；不初始化项目，不自动选规范。
3. 实现规范相对路径、文件类型、目录真实位置及受管布局检查，拒绝契约列出的软链／硬链接／越界及路径冲突。
4. 实现存在／缺失文件描述、目录直接成员描述、完整基线摘要和规范 JSON 摘要。输入来源身份与当前目标保护身份分开。
5. 实现进程内读取／检查凭证管理器：有效期、容量、项目／运行基线绑定和消费时机都按契约；不把凭证当多用户鉴权。
6. 统一成功和失败的返回字段、checks／issues、error 和空值。未运行的检查必须 `checked=false, passed=null`。

退出依据：可在临时中文项目中识别身份；不合法路径和参数无文件副作用；摘要稳定可重算；凭证使用可注入时钟测试，不用长时间等待。

### S5-A3：上下文、当前集合、历史和事务只读检查

依赖：A2。交付：三个只读工具的对应逻辑及 `versions.py` 读取能力。

1. 固定输入闭包、追加参考、导入描述、当前清单／指针／成员、未知目录和登记引用均按契约读取；缺失、不可读、损坏分开。
2. 对完整闭包做读取前后核对，稳定才签 read_id；Draft、无可选 tech-spec 等情况形成诊断，不伪造确认门槛。
3. 区分 empty、managed、legacy、unsupported 和 incomplete；公共文件漂移不自动纳管，首次存在未受管目标不自动覆盖。
4. 实现公共 file-set 清单与版本 packet 校验、二进制摘要、历史分页和单版本读取；不得覆写损坏历史。
5. 实现事务只读检查：校验计划和证据，按真实字节区分 before／after／other，报告活动／未激活状态与可用动作，不执行恢复。
6. 落实成员／字节／元数据／闭包／响应预算等限制；可以省略响应正文并明示，不能缩小保护描述后发凭证。

退出依据：只读场景前后整个项目和基础树完全相同，含目录、锁、回执、缓存；只读历史可以使用标明的静态夹具，但不报告 accept 已通过。

### S5-A4：stdio 最小只读链路

依赖：A3。交付：`mcp_server.py` 的启动、握手、工具发现和只读调用。

按基础服务实际协议实现并验证握手版本、元数据、消息限额、JSON-RPC 错误与工具业务错误分层。默认 tools/list 仅三项；构造写调用也返回 tool_not_enabled。新进程真实完成握手 → list → read → inspect → history；stdout 只用于协议。

5A 阶段退出：只读能力及本段适用测试可运行；没有业务写接口冒充实现。报告 5A 已完成不能升级为步骤 5 全部完成。

## 5. 5B：候选准备、导入与检查

### S5-B1：准备工作区和准备回执

依赖：5A。交付：`workspace.py` 准备逻辑及相关回执设施。

1. 在公共锁内复核 read_id 基线、活动事务、准备配额和请求 ID，再建立专属 R-id 工作区。
2. 支持 empty／current／import／history；按模式条件拒绝不合法调用。history 采用当前输入基线，保留 restored_from，不声称旧内容已适配新来源。
3. base.json 固定准备事实；candidate.json 和 tree 为允许编辑部分。公共成员、清单、当前指针均不变。
4. 导入只复制读取凭证已绑定的明确文件，按第 5.2 节映射；授权根只能增加只读来源，不扩写范围。
5. 开始建立工作区时消费 read_id。prepared 回执和失败残留按契约记录；相同请求重放返回原工作区，允许候选已被合法编辑。
6. 未完成准备不自动续拷或删除；配额包含残留，报告位置和下一步。关闭写能力时连私有工作区也不能创建。

退出依据：四种模式有正向证据；五文件导入映射正确且源不变；工作区可在重启后重新检查，旧内存凭证失效；相同准备请求不生成第二个工作区。

### S5-B2：候选完整检查和检查凭证

依赖：B1。交付：`ui_inspect(target=candidate)` 的完整实现。

1. 核对候选身份、不可编辑基线、完整实际 tree 与候选声明；仅按契约排除固定缓存名，不能任意忽略未知文件。
2. 检查本地 HTML 入口、设计说明、演示 README、成员范围／类型／限额、重复路径及依赖声明；不执行 HTML／JS，也不声称验证了所有浏览器资源引用。
3. 复核来源、当前目标、已登记引用与运行基线，输出 added／modified／removed 以及明确文件问题。
4. 计算 base_digest、candidate_digest、proposed_revision_sha256；通过时签 inspection_id，绑定删除集和完整候选。
5. 缺浏览器证据、业务待决项与文件阻断分开报告，不修改候选内容来凑通过。

退出依据：缺文件、未列成员、超限、候选元数据损坏、来源变化均不发凭证；合法二进制成员不经过文本解码；修改候选后旧检查凭证不能用于接收。

5B 阶段退出：可通过工具准备候选，由普通文件编辑器补齐完整成果，再获得真实检查结果。尚无接收成功证据时，继续标明公共保存未完成。

## 6. 5C：接收、历史、回执和基本恢复

### S5-C1：不可变版本和事务准备

依赖：5B。交付：版本写入、事务计划和 before／after 存储。

1. 按契约计算规范 packet 与内容身份，来源和成果共同参与，时间不进入摘要；避免把当前输出纳入自身来源造成循环。
2. 完整旧集合先归档，合法无指针旧集合标为 legacy；同 SHA 版本已存在必须完整核验后复用，不修补损坏版本。
3. 事务固定所有将写／删目标、公共清单、当前指针的 before／after 字节和 missing 状态；元数据交叉摘要、路径、版本及身份校验完整。
4. 对计划、版本和固定字节完成持久化，再建立活动日志；此后才可修改公共目标。预激活失败不得伪称已保存。

退出依据：可以从固定事务证据重算计划和每个目标的预期状态；事务准备失败不改公共成果，残留被准确报告。

### S5-C2：受控接收和完整复读

依赖：C1。交付：`ui_accept_revision`。

严格按契约第 7.1 节执行，不用整体复制目录替代：

1. 公共锁内先核对请求回执，再核对凭证、来源、候选、目标、登记引用、未知目录和删除集。
2. 输入和成果完全相同走 unchanged，只记合法回执，不重写公共成员或创建重复版本。
3. 固定事务并激活日志，按契约消费检查凭证；逐文件修改前再次核对实际目标，保护外部编辑。
4. 写成员／受管删除 → 公共清单 → current 指针，使用已验证原子替换和同步原语。不得宣称整集合原子可见。
5. 复读成员、清单、指针、历史、输入及未知文件，成功落终态回执后结束活动日志。
6. 如实区分 saved、unknown、saved_unverified、not_written；错误发生后返回事务及检查动作，不盲目重试或清理证据。

退出依据：首次和后续接收、增删成员、同内容复用、来源变更、用户冲突、已登记引用和未知文件保护均有实际文件断言。

### S5-C3：持久回执、并发和服务重启

依赖：C2，可随 C1／C2 同步实现。交付：准备／接收／恢复请求统一幂等处理。

1. request_id 绑定 operation 和准确参数摘要；相同已完成请求重放不二次写入，不同参数复用拒绝，未完成请求报告 operation_incomplete。
2. 重启后仍可核验并返回已完成回执，即使旧内存令牌失效；回放必须说明 receipt_replay，并独立报告实际当前版本。
3. 损坏回执和不可变版本拒绝；prepared 回放不因候选合法编辑误报损坏；已结束候选不再签新的检查凭证。
4. 公共锁协调既有 Main；Main 根事务阻止 UI 写入，不由 UI 接管。锁占用或遗留不自动删除。

退出依据：重复、并发、跨项目／候选凭证、重启续检和终态回执回放均得到正确结果及写次数／文件快照证据。

### S5-C4：基本恢复／回滚及历史再编辑

依赖：C1—C3。交付：`ui_recover_revision` 和历史候选完整主线。

1. 先实现事务检查，再依据显式 resume／rollback 请求执行；计划、字节、身份、来源和回执逐项核验。
2. resume 仅处理合法 before／after 且来源未变的事务；rollback 仅恢复已知 before，在无终态 saved 回执时执行。第三方 other 状态一律拒绝覆盖。
3. saved 回执已落盘后只允许校验并结束遗留日志；已提交的业务版本回退走 history 候选，不将 rollback 当旧版选择器。
4. 覆盖首次创建撤回、来源变化拒绝 resume、预激活事务只关闭私有记录，以及损坏计划／证据不足拒绝等基本分支。
5. 使用测试内部注入点或临时子进程制造中断；不增加 MCP force／fail_after 或跳过保护参数。遗留锁清理由临时夹具明确执行，不包装成工具自动能力。
6. 从历史 prepare → 依据当前输入编辑 → inspect → accept → 复读，证明中间版本仍完整保留。

退出依据：基本恢复算法和关键拒绝分支已实现且有运行证据。步骤 6 后续补齐各中断位置、真实进程退出、存储故障等系统矩阵；不得以“第 6 步再做”为由省略本段保护。

### S5-C5：六工具服务与净化环境主线

依赖：C4。交付：完整服务、端到端测试和实际报告。

1. 完成六工具 schema、严格参数和能力开关，新进程分别验证只读三项／允许写六项。
2. 用 `-I -S -B` 启动临时副本，净化路径和环境、设置同名诱导模块，确认无旧脚本／方案服务／真实工作区回退，完整跑通读写和适用恢复。
3. 每个写操作比较项目允许区和所有保护区，记录准确变化；禁止区字节及目录不变。
4. 按第 8 节跑完整主线，按第 9 节生成自验报告和逐场景账本。仅对已实现和已验证范围更新入口及来源说明。

5C 阶段退出：第 10 节步骤 5 完成条件全部满足；第 6、8、9 步状态独立保留。

## 7. 测试如何从旧清单落到本轮实现

既有清单是先写的验收规格。开发时为各场景编写可执行测试、准备临时数据、调用真实实现，再比较结果与文件。规格存在不等于用例已运行；一个 UI-T 编号可对应多个测试函数和子场景。

### 7.1 分段覆盖安排

| UI-T 范围 | 第 5 步落实 | 后续保留 |
| --- | --- | --- |
| T01—T09 | 5A 依赖、项目、闭包、路径、限额及布局；后续写工具接通后复验相关拒绝效果 | 变化后按影响复验 |
| T10—T20 | 5B 候选、导入、检查、凭证、重启和配额；接收消费相关断言在 5C 补齐 | 未覆盖组合逐子场景记录 |
| T21—T32 | 5C 保存、变更、历史、回执、登记引用和并发保护 | 不因主线成功省略拒绝断言 |
| T33—T42 | 5C 至少验证：预激活失败不写、部分写入可识别、已知状态 resume／rollback、saved 回执后拒绝回滚、来源变更拒绝 resume、第三方 other／坏计划拒绝 | 第 6 步按原规格补全所有指定中断位置、退出／重启、复读／磁盘／锁故障及组合；未全覆盖的 UI-T 不标整项通过 |
| T43 | 对实际实现重新核对 schema、文档、来源与能力，不沿用步骤 4 静态结论替代 | 第 7 步按最终实现全面校准 |
| T44 | 真实 stdio 握手、工具发现、调用、参数／消息及能力开关 | 第 9 步另做真实客户端链路 |
| T45—T47 | 本步已实现路径的新进程隔离、写范围和结果诚实；恢复相关按实际子场景记录 | 第 6 步扩展恢复后复验对应分支 |

T33—T42 的最低集合是步骤 5 的基本保护验证，不改变原清单的完整要求。若某个主编号仍有未执行子场景，主编号记 `partial`，列出已验子场景及证据，不能把部分执行记作该项全部通过。

### 7.2 有效测试要求

- 正向检查实际返回和完整文件内容；拒绝场景检查错误码、write_outcome、凭证消费事实、公共文件与私有副作用，而非仅断言“抛了异常”。
- 目录／成员与原始字节共同核对；只读操作连锁、缓存、目录也不新增。二进制、不存在目标、未知文件和用户新改动分别覆盖。
- 在内部时间／文件系统／事务阶段边界注入变化，验证读取中、检查后、接收中等不同时间点，不只在调用前放坏文件。
- stdio 测试启动真实新进程并解析真实响应；不能只直接调用 Python 函数就宣布协议可用。
- 测试不得复制实现算法再相互印证；使用固定输入、独立摘要重算、允许／禁止范围对比和外部可观察结果。
- 每段先运行对应测试；修改后复验受影响项。完整实现跑一次聚合测试，稳定通过后只在新变更或未解问题要求时扩展重跑。

计划聚合命令，从工作区根运行，测试文件实际存在后执行：

```sh
python3 -B -m unittest discover -s fusion-runtime/tests -p 'test_ui_*.py'
```

记录发现的测试数、实际执行数和退出码；零测试不算通过。净化子进程与 stdio 是测试中的独立执行记录，不用聚合退出码代替其证据。普通测试失败先修实现／夹具，不能删除用例或放宽契约来完成阶段。

## 8. 必须实际跑通的临时项目主线

使用初始化能力建立临时中文项目；PRD 为 Draft、tech-spec 可缺失。输入均为虚构测试材料。

| 顺序 | 实际动作 | 必须留存的事实 |
| --- | --- | --- |
| 1 | 只读启动并 read_context；检查空当前集合 | 正确项目 ID、完整来源描述、read_id；整个树无新增文件 |
| 2 | 允许写服务重新读取，prepare(empty) | 专属 revision_id、工作区、准备回执；公共成果未变 |
| 3 | 普通编辑器在候选中写入口、JS、CSS、预设旧素材、设计和 README，更新候选声明 | 候选完整文件表与原始字节摘要；编辑不写公共成果 |
| 4 | inspect(candidate) | 差异、候选摘要、来源／基线及 inspection_id |
| 5 | accept(delete_paths=[]) | saved、事务及请求引用；完整版本、清单和指针互相一致 |
| 6 | 新 read_context／inspect(current) 并 read_history | 复读与实际公共字节一致；能查到首版且无活动事务 |
| 7 | prepare(current)，修改 JS、增加素材、删除一个预设旧素材，再 inspect／accept | 精确删除集、第二版及旧版完整性；未知文件保留 |
| 8 | 重放相同保存请求，再提交内容／来源不变的新候选 | 前者 receipt_replay 无二次写；后者 unchanged 不新建重复版本 |
| 9 | 从历史 prepare(history)，按当前输入检查并正常接收 | restored_from 与来源正确；中间历史不丢失 |
| 10 | 在独立临时项目导入虚构五文件并接收 | 映射正确，原导入树字节和成员不变 |
| 11 | 分别制造检查后来源变化、目标变化、越界路径和写能力关闭 | 明确拒绝与文件对比；不用同一破坏状态串跑掩盖失败原因 |
| 12 | 在独立夹具中断接收、inspect(transaction)、显式恢复；再制造 other 状态 | 已知状态可核对恢复，第三方改动完整保留；无隐式删锁／强制覆盖 |

B1、B2、H 夹具在 5C 集成验证必须由真实工具接收生成。5A 手工历史夹具不能充当上述第 5—9 项的成功证据。

## 9. 开发报告、测试账本与继续方式

### 9.1 每完成一段记录什么

开发 Agent 在实际报告中维护：采用契约和源码摘要、当前阶段、已完成任务 ID、改动文件、真实命令／退出码、测试映射及结果、文件副作用、失败与修复、后续待验项和下一任务。

若需中途交接，记录最后一个通过的阶段、未完成候选／事务、临时环境是否保留及准确位置。新会话先核对实际文件和基线再续做；不从本文的计划列表推断文件已经存在。

### 9.2 测试结果账本

`step5-test-results.json` 由实施 Agent 根据真实执行生成，至少包含：

| 层级 | 必要信息 |
| --- | --- |
| 报告头 | schema_version、contract_version、阶段、生成时间、执行环境、代码／测试文件摘要 |
| 场景 | UI-T 编号、稳定子场景标识、测试函数、状态、实际命令／请求、预期、实际结果、证据文件、未验原因 |
| 文件证据 | 项目身份、当前／候选／历史摘要、允许变化、禁止区前后对比、事务与回执引用（适用时） |
| 汇总 | 测试函数执行数、UI-T 主编号完整通过数／部分覆盖数／未运行数／失败数，分别统计 |

状态使用 `passed`／`failed`／`not_run`／`blocked`／`partial`，并说明状态适用于主编号还是子场景。未运行用例的实际结果保持空值，不能补写预期为实际。

开发自验报告采用本节计划路径；后续测试者按[验收执行文档](ui-step5-acceptance-test.md)另建本轮 acceptance-runs 记录，不覆盖开发报告或既有静态证据。自验与独立执行者结论分开。

### 9.3 规则与来源同步

新增采用源码后写入 SOURCES 的实际摘要；保留原来源和变更理由。共享依赖摘要仍代表原采用版本，不能以新实现方便为由改写。

ui-design、文件约定和 README 只描述已经可用的能力、实际启动方法及仍未验证的范围。文档可以分段同步避免误导；第 7 步仍对最终实现做完整校准。建设进度、开发计划、测试证据不进入工具运行代码基线，避免普通状态更新让服务不可用。

真实客户端配置、正式成果登记和浏览器体验证据保持各自后续步骤，不因文件工具自验通过而改写为已完成。

## 10. 步骤 5 完成条件和停点

只有同时满足以下条件，才把建设进度中“步骤 5”改为完成其实现与自验范围：

1. 六工具及能力开关实际实现，参数、返回和错误与 ui-tools-v1 一致。
2. 第 8 节完整主线在临时项目通过，取得可重跑的真实调用与文件证据。
3. 冲突、越界、输入／候选变动、未知文件、登记引用、重复请求、只读副作用等本步必需保护通过。
4. 基本恢复／回滚及 other／来源变化／终态回执等拒绝分支已实现并验证；未完成的系统故障矩阵明确列在第 6 步。
5. stdio、新进程净化运行、准确写范围及保护区不变有证据。
6. 本步适用测试无未解决失败；缺少主线或必需保护证据时保持“进行中”，不能只因代码存在记完成。
7. 开发报告、账本、来源与实际能力一致；T01—T47 每个编号都有明确覆盖状态，未执行项不冒充通过。

满足后可报告 `DEV_READY_FOR_REVIEW`，但结论限定为开发自验。步骤 3 后补、步骤 6 全矩阵、步骤 8 独立验证、步骤 9 真实客户端试点分别保留状态。没有明确授权时不启动独立验收 Agent，不自动切换客户端或接收真实采购成果。

发现契约未决且影响安全写入时停止相关写入分支，说明具体条款和所需决定，继续不受影响的只读／测试工作。发现依赖漂移、损坏或权限不足时如实记录，不换源、不刷新锁、不清除用户文件来继续。
